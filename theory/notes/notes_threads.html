1
std::thread Basics

std::thread is a thin RAII-shaped wrapper around a native OS thread (pthread on POSIX, HANDLE on Windows). Constructing one launches it immediately — there is no separate "start" call.

basic_thread.cpp
1 void worker(int id) { 2 std::cout << "worker " << id << " running\n"; 3 } 4 5 std::thread t(worker, 7); // starts running immediately, on construction 6 // ... do other work on the calling thread ... 7 t.join(); // block until t finishes

Every std::thread object is in exactly one of two states with respect to the OS thread it may own: joinable or not joinable. A default-constructed thread, a moved-from thread, and a thread that has already been join()ed or detach()ed are all not-joinable. t.joinable() answers this directly — checking it before calling join() or detach() avoids the exception both throw when called on a non-joinable thread.

join()

Blocks the calling thread until t finishes. After it returns, t is no longer joinable. The standard, safe default — the calling thread knows exactly when the work is done.

detach()

Severs the std::thread object from the OS thread, which now runs fully independently and cleans itself up on exit. t is no longer joinable, and there is no way to wait on or observe a detached thread again.

⚠ Neither Join Nor Detach → std::terminate
If a std::thread object is still joinable when its destructor runs, the destructor calls std::terminate() — not a clean-ish exception, an immediate abort of the whole process. This is a deliberate design choice: the library refuses to guess whether you meant to wait or abandon the thread, so every code path (including exception-unwinding paths) must explicitly resolve every joinable thread before it goes out of scope.

1.1 Passing Arguments

Arguments to the thread function are copied (or moved) into internal storage owned by the std::thread object, then passed to the invoked function as rvalues. This has a sharp, well-known consequence for reference parameters.

reference_args.cpp
1 void increment(int& x) { ++x; } 2 3 int counter = 0; 4 std::thread t(increment, counter); // WON'T COMPILE — copies counter into storage, 5 // then tries to bind int& to an rvalue int 6 std::thread t2(increment, std::ref(counter)); // correct — std::ref wraps a real reference 7 t2.join(); 8 // counter is now 1
💡 std::ref / std::cref
std::ref(x) produces a std::reference_wrapper<T> — a small copyable object that behaves like a reference for the purposes of argument deduction. It's the standard way to make a thread (or std::bind, or std::async) target a reference parameter without accidentally decaying to a by-value copy.

Move-only arguments (a std::unique_ptr<T>, for instance) transfer cleanly: std::thread t(worker, std::move(ptr)) moves ownership into the thread's internal storage, and the worker function receives it by value or by rvalue reference.

Thread Identity & Hardware Concurrency

t.get_id() returns a std::thread::id — an opaque, totally-ordered, hashable value usable as a map key or for logging, but with no arithmetic meaning. std::this_thread::get_id() gets the calling thread's own id. std::thread::hardware_concurrency() returns a hint (0 if unknown) at how many threads can genuinely run in parallel — commonly used to size a thread pool, though it's advice, not a guarantee.

2
RAII & Thread Lifecycle

Because a joinable thread left dangling terminates the process, and because exceptions can unwind past a join() call before it runs, threads are a textbook case for RAII: wrap the thread in a small guard object whose destructor resolves it unconditionally.

thread_guard.hpp
1 class ThreadGuard { 2 public: 3 explicit ThreadGuard(std::thread t) : t_(std::move(t)) {} 4 5 ~ThreadGuard() { 6 if (t_.joinable()) t_.join(); 7 } 8 9 ThreadGuard(const ThreadGuard&) = delete; 10 ThreadGuard& operator=(const ThreadGuard&) = delete; 11 ThreadGuard(ThreadGuard&&) = default; 12 ThreadGuard& operator=(ThreadGuard&&) = default; 13 14 private: 15 std::thread t_; 16 };

Copying is deleted for the same reason it's deleted on std::thread itself — a thread of execution has exactly one owner, so the type is move-only. Wrapping it in a vector needs std::vector<ThreadGuard> (works fine, since the type is movable) or a vector of std::unique_ptr<ThreadGuard> if the guard itself must stay pinned in memory.

◈ Destructor Order Is Reverse-Declaration Order
A vector of ThreadGuard destroys elements in order — but a hand-rolled worker pool with several distinct guard members destroys them in reverse declaration order, same as any other class. If a shutdown sequence needs threads joined in a specific order (e.g. producers before consumers), that ordering has to be either explicit in a dedicated shutdown() method, or encoded directly in the members' declaration order — relying on implicit destructor order for correctness is fragile and easy to break with an innocuous reordering.

2.1 Shutdown Ordering

In any multi-thread system with a natural producer→consumer direction, a clean shutdown is a protocol, not a single call. The typical sequence:

  1. Stop producing new work (close the input, signal "no more items coming").
  2. Wake anything blocked waiting for work (a condition variable notify, or a poison-pill value pushed onto a queue).
  3. Join upstream/producer threads first, so no thread downstream can receive work from a thread that's already gone.
  4. Join downstream/consumer threads once producers are confirmed done and queues are drained.
⚠ Joining Out of Order Can Deadlock
Joining a consumer before its producer has stopped (and drained) risks the consumer blocking forever on an empty queue that will never receive more data, while the producer thread — still running — is never given the chance to finish and signal completion. The join direction should mirror the data-flow direction: stop the source, then join downstream in flow order.

2.2 std::jthread (C++20)

std::jthread is a drop-in upgrade over std::thread that fixes the most common footgun directly in the type: its destructor automatically requests a stop and joins if still joinable, so a jthread going out of scope never terminates the process.

jthread_basic.cpp
1 void loop(std::stop_token tok) { 2 while (!tok.stop_requested()) { 3 // ... do work in small increments ... 4 } 5 } 6 7 { 8 std::jthread jt(loop); 9 } // scope exit: destructor calls request_stop() then join() — no manual cleanup needed

If the target function's first parameter is a std::stop_token, jthread passes one in automatically, letting the function poll stop_requested() cooperatively. This replaces the common hand-rolled pattern of an std::atomic<bool> stop_flag shared between the launching code and the worker.

jthread is still cooperative cancellation, not preemptive — a worker that never checks stop_token (e.g. it's blocked on a long condition-variable wait without a predicate, or a blocking I/O call) won't actually stop just because a stop was requested. std::stop_token composes with condition_variable_any::wait, which can wake early on a stop request.

3
Data Races & the Memory Model

A data race has a precise definition in the C++ standard: two or more threads access the same memory location concurrently, at least one access is a write, and the accesses are not synchronized with each other. A data race is undefined behavior — not "probably wrong," but licenses the compiler and hardware to do anything, including things that look impossible when reading the source (a variable appearing to have a value it was never assigned, or a loop that never observes a flag change and spins forever because it was hoisted out of the loop entirely).

⚠ Race Condition vs. Data Race
These terms are often used interchangeably but aren't the same thing. A race condition is a broader, language-agnostic term for any outcome that depends on the relative timing of events — it can exist even with perfect synchronization (e.g. two properly-locked threads racing to be "first" to insert a key, where either outcome is a legal, defined result). A data race is the specific, C++-standard, UB-triggering case of unsynchronized concurrent access to the same memory. Every data race is a bug; not every race condition is.

3.1 Sequenced-Before and Happens-Before

Two relations underpin the whole model. Sequenced-before is the single-threaded ordering — statement A is sequenced-before statement B if A is required to complete before B begins, per ordinary program order and evaluation rules. Happens-before extends this across threads: it's built from sequenced-before plus synchronizes-with edges, which are created by specific synchronization operations (unlocking a mutex that another thread later locks, or a release-store paired with an acquire-load on the same atomic).

FIG 1 — a release/acquire pair on `ready` is what makes the write to `data` visible to thread B

This is the load-bearing guarantee behind every synchronization primitive in the standard library: a mutex unlock synchronizes-with the next lock of the same mutex, a thread's completion synchronizes-with the join() that observes it, and a condition-variable notify synchronizes-with the wait it wakes (once the predicate is re-checked under the lock). Without one of these established relationships, the compiler and CPU are both free to reorder, and there is no guarantee thread B ever observes thread A's writes at all — not "might see a stale value," but no defined ordering exists between the two accesses.

◈ Why Just "volatile" Doesn't Fix It
volatile in C++ only tells the compiler not to elide or reorder accesses to that specific variable relative to other volatile accesses — it has no defined interaction with the C++ memory model, provides no atomicity, and generates no memory fences. It's the right tool for memory-mapped hardware registers and signal handlers, and the wrong tool for inter-thread communication; that's what std::atomic is for.
4
Mutexes & Locking

A mutex (mutual exclusion) guarantees that only one thread at a time can hold the lock guarding a critical section. The standard library provides several flavors and, more importantly, several RAII wrappers so a mutex is never left locked by an early return, a thrown exception, or a forgotten unlock.

TypeBehavior
std::mutexBasic non-recursive, non-timed mutex. Locking it again on the same thread that already holds it is undefined behavior (typically deadlock).
std::recursive_mutexSame thread may lock it multiple times; must unlock the same number of times. Usually a sign of a design that could be refactored — genuinely necessary in some reentrant call chains.
std::timed_mutexAdds try_lock_for / try_lock_until — attempt to acquire, give up after a duration or deadline instead of blocking forever.
std::shared_mutex (C++17)Readers-writer lock: any number of concurrent shared (read) locks, or one exclusive (write) lock, never both. Use with std::shared_lock for readers.

4.1 RAII Lock Wrappers

std::lock_guard<M>

Minimal — locks on construction, unlocks on destruction. No unlock-and-relock, no ownership transfer, no default constructor. The lightest-weight choice when the lock is held for the guard's entire scope.

std::unique_lock<M>

Everything lock_guard does, plus: deferred locking, manual lock()/unlock() mid-scope, movable ownership, and — critically — it's the type std::condition_variable::wait requires, since waiting must be able to unlock and later re-lock.

raii_locking.cpp
1 std::mutex m; 2 int shared_counter = 0; 3 4 void increment() { 5 std::lock_guard<std::mutex> lock(m); // locked here 6 ++shared_counter; 7 } // unlocked here, even if an exception was thrown above
💡 std::scoped_lock (C++17) for Multiple Mutexes
std::scoped_lock lk(m1, m2, m3); locks all of them together using a deadlock-avoidance algorithm internally (equivalent to std::lock), instead of locking them one at a time in a fixed order that could interleave badly with another thread locking the same set in reverse order. Prefer it any time a single critical section needs more than one mutex held simultaneously.

4.2 Deadlock & Lock Ordering

The classic deadlock: thread A holds mutex 1 and waits for mutex 2; thread B holds mutex 2 and waits for mutex 1. Neither ever proceeds. This is one instance of the more general four Coffman conditions for deadlock — mutual exclusion, hold-and-wait, no preemption, and circular wait — and breaking any one of the four prevents it.

FIG 2 — classic two-mutex deadlock: reverse lock order between two threads
⚠ Fixes for Lock-Order Deadlock
Three standard escapes: (1) always acquire multiple mutexes in the same global order across every thread, e.g. by address or by an assigned rank; (2) use std::lock / std::scoped_lock to acquire several mutexes atomically as a set; (3) avoid holding more than one lock at a time in the first place — often achievable by narrowing critical sections or by copying data out under one lock before touching a second resource.

A single mutex can also self-deadlock: a non-recursive std::mutex locked twice by the same thread (e.g. a public method that locks, then calls a private helper that locks again) blocks forever, since the thread is waiting on a lock it itself already holds and cannot release until it acquires the very lock it's waiting for.

5
Condition Variables

A mutex alone can only protect data — it can't make a thread wait efficiently for a condition to become true. Busy-polling a flag under a lock burns CPU and adds lock contention; std::condition_variable lets a thread sleep until another thread explicitly wakes it.

condvar_basic.cpp
1 std::mutex m; 2 std::condition_variable cv; 3 bool ready = false; 4 5 // waiting side 6 std::unique_lock<std::mutex> lock(m); 7 cv.wait(lock, [] { return ready; }); // predicate form — the safe default 8 // ready == true here, and lock is held again 9 10 // notifying side 11 { std::lock_guard<std::mutex> lg(m); ready = true; } 12 cv.notify_one();

The predicate-taking overload of wait is equivalent to while (!pred()) wait(lock); — it re-checks the condition in a loop, re-acquiring the lock each time it wakes, until the predicate holds. This single call handles two separate real problems at once.

Spurious Wakeups

The standard permits a waiting thread to wake up even though no one called notify — an artifact of how condition variables are implemented on top of OS primitives. A bare wait(lock) with no predicate must always be wrapped in a loop that re-checks the actual condition; the predicate overload does this automatically.

The Lost Wakeup

If the notifying thread sets ready = true and calls notify_one() before the waiter has started waiting, and the waiter isn't re-checking the flag on entry, the notification is missed entirely and the waiter can block forever. The predicate form fixes this too — it checks pred() before ever blocking, so a notification that "arrived early" is still observed.

⚠ Always Modify the Predicate State Under the Same Mutex
The flag or queue state that the predicate reads must be modified while holding the exact mutex passed to wait — otherwise there's a data race between the notifier writing ready and the waiter's predicate reading it, independent of whatever the condition variable itself does. The condition variable coordinates when to re-check; the mutex is what makes the check itself race-free.

5.1 notify_one vs. notify_all

CallWakesTypical use
notify_one()At most one waiting thread (which one is unspecified).One unit of work became available for exactly one consumer — e.g. one item pushed to a work queue.
notify_all()Every currently-waiting thread.A state change every waiter needs to re-evaluate — most importantly, shutdown: every worker must wake up and observe "stop requested," not just one of them.

It's always safe to use notify_all() where notify_one() would suffice — the woken threads that find the predicate still false simply go back to sleep — it's only a (usually minor) efficiency cost, not a correctness one. The reverse — using notify_one() when the situation actually needs every waiter awake, such as shutdown — is a correctness bug.

5.2 condition_variable_any

std::condition_variable only works with std::unique_lock<std::mutex>. std::condition_variable_any is the more general (and slightly more expensive) version that works with any lockable type, including std::shared_lock — and, since C++20, it's the version that composes with a std::stop_token to support waking early on a cooperative-cancellation request.

6
Atomics & Memory Order

std::atomic<T> gives a variable two guarantees a plain variable doesn't have: every operation on it is indivisible (no thread ever observes a "half-written" value), and each operation can be tagged with a memory order that controls what reordering is and isn't allowed around it. For small trivially-copyable types (bool, integers, pointers) most platforms implement this without any locking at all — is_lock_free() reports whether that's true for a given specialization.

atomic_flag.cpp
1 std::atomic<bool> done{false}; 2 3 // worker thread 4 while (!done.load()) { // do work chunk } 5 6 // controller thread 7 done.store(true);
💡 std::atomic vs. std::mutex
An atomic is the right tool for a single flag, counter, or pointer where the only operations needed are load/store/increment/CAS. A mutex is the right tool the moment more than one related piece of state must change together consistently — atomics don't compose: making two separate atomics individually thread-safe does not make the pair of them consistent with each other.

6.1 Memory Orders

Every atomic operation takes an optional std::memory_order argument (default seq_cst). This is the part of the language most often quoted incorrectly in interviews, so the precise roles:

OrderApplies toGuarantee
relaxedload, store, RMWAtomicity only — no ordering guarantee relative to other memory operations on other variables. Use for independent counters (e.g. a stats/drop counter) where only the final total matters, never as a synchronization signal.
releasestoreNo read/write in this thread, before the store, may be reordered after it. Publishes prior writes to whichever thread later does a matching acquire load.
acquireloadNo read/write in this thread, after the load, may be reordered before it. Makes the writes that preceded a matching release store visible.
acq_relread-modify-writeAcquire on the read part, release on the write part — the standard choice for an RMW op (e.g. fetch_add) that both consumes and publishes state.
seq_cstall ops (default)Everything acquire/release give, plus a single global total order that every thread agrees on for all seq_cst operations. The safest default; also the most expensive on some architectures.
◈ The release/acquire "Handshake" Pattern
The pattern in Section 3's diagram — one thread does flag.store(true, release) after writing shared data, another does while (!flag.load(acquire)); before reading it — is the single most common correct use of non-default memory orders. It's cheaper than seq_cst on architectures with weaker native memory models (ARM in particular) while still being fully race-free, because the release/acquire pairing on the same atomic establishes the happens-before edge that makes the data write visible.

6.2 Compare-Exchange & the ABA Problem

compare_exchange_weak / compare_exchange_strong are the building blocks of lock-free algorithms: "if the atomic still holds the value I last read, replace it with a new value; otherwise, tell me what it actually holds now." The weak version may fail spuriously even when the comparison would have succeeded (cheaper on some platforms, e.g. LL/SC architectures) and is meant to be used in a retry loop; the strong version never fails spuriously and is the right choice outside a loop.

cas_increment.cpp
1 std::atomic<int> counter{0}; 2 3 int old_val = counter.load(std::memory_order_relaxed); 4 int new_val; 5 do { 6 new_val = old_val + 1; 7 } while (!counter.compare_exchange_weak(old_val, new_val)); 8 // on failure, old_val is updated to the current value automatically — loop retries

The ABA problem: a compare-exchange only checks that the value is bitwise-equal to what was last read — it can't tell the difference between "nothing changed" and "it changed away from A, to something else, and back to A again" between the read and the CAS. For a plain counter this is harmless. For a pointer-based structure (e.g. a lock-free stack's head pointer), a node can be popped, freed, and a new node reallocated at the exact same address, making a stale CAS succeed against a completely different logical state — a classic source of subtle lock-free-data-structure corruption. Standard mitigations: tagged pointers (pack a version counter alongside the pointer bits) or hazard pointers / epoch-based reclamation to prevent premature reuse of freed memory.

7
Futures, Promises & Async

Threads plus mutexes plus condition variables can express any concurrent computation, but for the common case of "run this, and give me the result later," the standard library offers a higher-level, result-carrying abstraction that avoids hand-rolling the wait/notify plumbing.

std::promise<T>

The write side. One thread calls set_value(x) (or set_exception(...)) exactly once. Internally synchronizes with whoever holds the paired future.

std::future<T>

The read side. get() blocks until the value is ready, then returns it — and may only be called once, since it moves the result out.

promise_future.cpp
1 std::promise<int> p; 2 std::future<int> fut = p.get_future(); 3 4 std::thread producer([&p] { 5 int result = expensive_computation(); 6 p.set_value(result); 7 }); 8 9 int value = fut.get(); // blocks until set_value() runs 10 producer.join();

7.1 std::async

std::async(policy, fn, args...) packages "run this function, possibly on another thread, and give me a future for the result" into one call, skipping the manual promise/thread wiring.

Launch policyBehavior
std::launch::asyncRuns on a new thread, guaranteed. Equivalent in spirit to std::thread + std::promise, but with automatic result plumbing.
std::launch::deferredNot run at all until .get() or .wait() is called — then runs synchronously on the calling thread, lazily.
async | deferred (default)Implementation's choice between the two — commonly a thread-pool-backed decision. This ambiguity is exactly why the explicit policy is usually preferred in code where "does this run concurrently" actually matters.
⚠ A future's Destructor Can Block
The future returned by std::async with the default (or async) policy has a special property: if it's the last future referring to that shared state and it's destroyed without get() or wait() ever having been called, its destructor blocks until the async task completes — effectively an implicit join. An unnamed temporary, std::async(...) as a bare statement with no variable to hold the future, is therefore fully synchronous in practice: the temporary future is destroyed at the end of the full expression, which blocks immediately. (A future obtained from a std::promise directly does not have this blocking-destructor behavior.)

7.2 std::packaged_task & shared_future

std::packaged_task<Sig> wraps a callable so that its result is delivered through a future, without the caller having to manage a std::promise by hand — useful for handing work items into a custom thread pool's queue, since the task itself is a single movable callable that can be stored in a queue of std::function<void()>-like wrappers.

std::future<T>::get() can only be called once (it moves the result out and invalidates the future). std::shared_future<T>, obtained via fut.share(), is copyable and allows multiple threads to each call .get() independently — the standard choice when more than one consumer needs to observe the same result.

8
Producer–Consumer & Queues

The producer–consumer pattern — one or more threads generating items, one or more threads processing them, decoupled by a queue — is the backbone of most real concurrent systems: pipelines, event loops, work-stealing pools, logging systems. The queue is the single piece of shared state, so its thread-safety design is the whole ballgame.

FIG 3 — a bounded queue decouples producer and consumer rates and is the one piece of shared state to get right

8.1 SPSC vs. MPSC vs. MPMC

The number of concurrent producers and consumers changes what a queue needs to guarantee, and cheaper implementations exist for narrower cases.

ShapeMeaningTypical implementation
SPSCSingle-producer, single-consumerA fixed-size ring buffer with two atomic indices (head owned by consumer, tail owned by producer) can be entirely lock-free — each side only ever writes its own index and reads the other's.
MPSCMulti-producer, single-consumerProducers now contend with each other on the tail index — needs either a mutex around the push, or a lock-free MPSC-specific algorithm (e.g. an intrusive linked-list queue with atomic CAS on the tail pointer).
MPMCMulti-producer, multi-consumerBoth ends contend. Usually simplest and often fast enough as a mutex + condition_variable bounded queue; genuinely lock-free MPMC queues are substantially more complex to get correct.
💡 Why Reach for Several SPSC Queues Instead of One Shared Queue
When work can be partitioned up front (e.g. sharded by some key so each item always belongs to exactly one consumer), giving each consumer its own dedicated SPSC queue avoids all cross-producer contention on a single shared structure, keeps each queue's implementation as simple and cheap as an SPSC ring buffer allows, and sidesteps the fairness question a single MPMC queue raises (which consumer gets the next item). The tradeoff is that a component wanting to know "is any queue non-empty" now has to check N queues, or be woken via a mechanism that can wake across many queues rather than waiting on a single one.

8.2 Backpressure

An unbounded queue can absorb any producer/consumer rate mismatch — right up until it exhausts memory. A bounded queue forces an explicit decision about what happens when it's full, which is a design choice, not an incidental detail:

Blocking push

The producer waits (condition-variable style) until space frees up. Preserves every item but couples the producer's throughput to the consumer's — a slow consumer directly throttles upstream production.

try_push / drop-and-count

A full queue rejects the new item immediately; the caller increments a drop counter (typically an std::atomic<uint64_t>) and moves on. Bounds latency for the producer at the cost of data loss — appropriate when freshness matters more than completeness, e.g. real-time telemetry.

A hybrid — push_wait(timeout) — blocks up to a bound before falling back to drop-and-count, trading a little latency for a lot fewer drops under transient bursts.

8.3 Waking a Consumer Across Multiple Queues

A single condition variable naturally pairs with a single mutex/queue. When one consumer thread must wake up whenever any of several independent queues receives an item (e.g. a publisher thread fanning in from many per-shard event queues), a single shared "wake" signal — one condition variable (or semaphore) that every producer notifies regardless of which queue it pushed to — lets the consumer block once and then scan all queues on wakeup, rather than requiring a separate waiter per queue.

9
C++20 Additions

C++20 added several purpose-built synchronization primitives that previously had to be hand-rolled on top of a mutex and condition variable — each one narrower than a general condvar, and correspondingly harder to misuse.

std::latch

A single-use countdown gate. count_down() decrements; wait() blocks until it hits zero. Common use: N worker threads each signal "initialized," and a coordinator waits for all N before proceeding. Cannot be reset or reused.

std::barrier

Like a latch, but reusable across phases — once all participants arrive, everyone is released together and the barrier resets for the next round. Fits lock-step parallel algorithms (e.g. every worker finishes phase 1 before anyone starts phase 2), and takes an optional completion callback that runs once per phase.

std::counting_semaphore<N>

acquire() decrements a count (blocking at zero), release() increments it. Naturally models a bounded resource pool (e.g. "at most K concurrent connections") — unlike a mutex, a semaphore has no notion of an "owning thread," so it can be released by a different thread than the one that acquired it.

◈ std::binary_semaphore as a Lightweight Signal
std::binary_semaphore is just counting_semaphore<1>, and is often the simplest tool for a one-shot "signal thread B that thread A finished a step" — cheaper conceptually than a mutex+condvar pair when there's no actual shared data to protect, only a signal to send.

Section 2.2 already covers std::jthread and std::stop_token, the other headline C++20 concurrency addition — cooperative cancellation that composes with condition_variable_any::wait to interrupt a wait early on a stop request.

10
Concurrency Design Patterns

Correct low-level primitives are necessary but not sufficient — most concurrency bugs come from a system's overall shape, not from misusing an individual mutex. A handful of recurring shapes cover most real designs.

10.1 Ownership Sharding

Rather than protecting one large shared structure with a lock, partition the data by some key (customer ID, symbol, shard index) so that each partition is owned exclusively by one thread. Correctness then comes from ownership, not from synchronization — a thread never needs to lock its own partition, because no other thread ever touches it. Cross-partition communication still needs synchronization (typically a queue per partition, see §8), but the hot-path data structure itself stays lock-free by construction.

💡 Why This Scales Better Than One Big Lock
A single mutex around one large structure serializes every thread on every access, regardless of whether their work actually overlaps. Sharding by ownership means N threads working on N disjoint partitions truly run in parallel with zero contention between them — the design eliminates the need for the lock entirely, rather than making the lock faster.

10.2 Pipeline Stages

Work flows through a fixed sequence of stages (e.g. ingest → process → publish), each running on its own dedicated thread, connected by a queue between each pair of adjacent stages. Each stage thread has a simple, single-purpose loop: pop from its input queue, do its transformation, push to its output queue. This keeps each stage's logic decoupled from the others' timing and makes throughput bottlenecks easy to isolate (whichever stage's queue backs up first is the bottleneck).

FIG 4 — a pipeline: each stage is one thread, connected by queues, each stage single-purpose

10.3 Thread Pools

A fixed set of worker threads, created once, pulling tasks (often std::function<void()> or packaged_task) from a shared queue, rather than spawning a new std::thread per unit of work. Thread creation is comparatively expensive (kernel-level allocation, stack setup); a pool amortizes that cost across the process's lifetime and bounds the number of concurrently-running threads to something sane relative to hardware_concurrency().

⚠ Unbounded Thread-Per-Task Doesn't Scale
Spawning a new thread for every incoming unit of work (a new connection, a new request) works fine at low load and degrades badly under bursts — thread creation cost, context-switch overhead, and memory for each thread's stack all scale linearly with concurrent load, with no ceiling. A bounded thread pool converts "how many threads exist" from a function of instantaneous load into a fixed, tunable constant.

10.4 Single-Threaded Ownership Inside a Worker

A recurring correctness technique: instead of making a data structure itself thread-safe (locks inside every method), confine it to exactly one thread and make everything else about the system route through that thread via message-passing (queues). The structure itself needs zero internal synchronization — every access to it is, by construction, single-threaded — which both simplifies its implementation and removes an entire category of bugs from it. The cost moves to the boundary: the queues feeding that thread must themselves be correctly synchronized, but that's a much smaller, well-understood surface than "make an arbitrary data structure thread-safe."

Pitfalls & Gotchas
  • Deadlock — circular wait on multiple locks (§4.2). Fix with a consistent global lock order, or std::scoped_lock.
  • Livelock — threads actively respond to each other (e.g. both back off and retry in lockstep) but make no forward progress, unlike deadlock's stillness. Randomized backoff, not just deterministic retry, is the usual fix.
  • Priority inversion — a low-priority thread holds a lock a high-priority thread needs, and a medium-priority thread (which needs no lock) preempts the low-priority one, indirectly blocking the high-priority thread indefinitely. Priority-inheritance mutexes are the classical OS-level fix; at the application level, keeping critical sections short is the cheapest mitigation.
  • False sharing — two unrelated atomics or variables used by different threads happen to sit on the same CPU cache line; every write to one invalidates the other thread's cached copy, causing costly cache-coherency traffic even though there's no logical data race. Fixed with padding or alignas(std::hardware_destructive_interference_size) (C++17) to force separation onto different cache lines.
  • Thundering herd — notify_all() wakes every waiter, but only one can proceed (e.g. only one item is available); the rest wake, re-acquire the mutex, find the predicate still false, and go back to sleep, wasting cycles under high contention. Where the workload allows it, notify_one() per available unit of work avoids this.
  • Forgetting to hold the mutex while reading shared state, not just while writing it — a data race requires only one side to be a write; an unprotected read racing against a protected write is still undefined behavior.
  • Calling a callback or virtual function while still holding a lock — if that call re-enters the same object and tries to lock the same non-recursive mutex, it deadlocks against itself; if it calls into unrelated code that happens to acquire other locks, it widens the surface for lock-order deadlocks.
  • Copying a std::thread, std::mutex, std::unique_ptr-holding guard, or similar move-only synchronization type into a container that assumes copyability (some older or third-party container templates) — fails to compile, but the fix (switch to a move-friendly container, or store by unique_ptr) is sometimes non-obvious from the error message.
  • Assuming std::atomic<T> for a non-trivial T is lock-free — it compiles for any trivially-copyable type, but larger types commonly fall back to an internal mutex; check is_lock_free() rather than assuming.

Self-Test

Tap a question to reveal the answer. Try answering in your head first — these are pitched at the level a technical interview would ask.

Why does a std::thread's destructor call std::terminate if it's still joinable, instead of just calling join() automatically?

An implicit automatic join in the destructor would silently block the calling thread — potentially for an unbounded time, and potentially causing a deadlock the caller never asked for — at a point in the code where nothing textually suggests a wait is about to happen. The library refuses to make that choice on the programmer's behalf. Requiring an explicit join() or detach() forces the decision to be visible in the code, and std::terminate makes an unresolved thread a loud, immediate failure rather than a silent hang.

What's the actual difference between a data race and a race condition?

A data race is the specific C++ standard term: unsynchronized concurrent access to the same memory location where at least one access is a write — it is always undefined behavior. A race condition is broader: any behavior that depends on the relative timing/interleaving of events, which can exist even in perfectly synchronized code (e.g. which of two properly-locked threads happens to insert first). Every data race creates a race condition, but plenty of race conditions involve no data race at all.

Why is the predicate form of condition_variable::wait almost always preferred over a bare wait(lock)?

It solves two distinct problems in one call: spurious wakeups (the standard permits a wait to return with no corresponding notify, so the actual condition must always be re-checked) and the lost-wakeup problem (a notify that arrives before the waiter starts waiting would otherwise be missed entirely). The predicate form is equivalent to looping while (!pred()) wait(lock);, which checks the condition before ever blocking and again after every wakeup.

Two threads communicate via a std::atomic<bool> flag: one writes data then stores the flag true; the other loads the flag then reads data. What memory orders make this correct, and why does memory_order_relaxed on both sides not work?

The store needs memory_order_release and the load needs memory_order_acquire (or both sides can use the default seq_cst). The release/acquire pairing on the same atomic establishes a happens-before edge, guaranteeing the write to data is visible once the acquire-load observes true. With relaxed on both sides, the flag update is still atomic, but nothing prevents the compiler or CPU from reordering the write to data to after the flag store on the writer's side, or reordering the read of data to before the flag load on the reader's side — the flag becoming visible carries no guarantee at all about the visibility of data.

Why can std::async's returned future block in its destructor, and how do you avoid that surprise?

When the default or std::launch::async policy is used and the returned future is the last one referring to that shared state, its destructor blocks until the asynchronous task finishes — effectively an implicit join baked into an object that doesn't look like a thread handle. This most commonly bites when std::async(...) is called as a bare statement with no named variable: the temporary future is destroyed at the end of the full expression, so the call becomes fully synchronous despite appearances. Avoiding the surprise means either holding onto the future deliberately and calling get()/wait() explicitly, or being aware that a discarded async call still blocks the calling thread right there.

What's the ABA problem, and why doesn't a plain compare_exchange loop protect against it on a lock-free stack's head pointer?

A CAS only checks bitwise equality against the last-read value — it can't distinguish "unchanged since I read it" from "changed away and back to the same bit pattern." On a lock-free stack, a node can be popped, freed, and a new allocation reused at the identical address, so a stale thread's CAS against the head pointer can succeed against a completely different logical stack state, corrupting it. Mitigations include tagging the pointer with a version counter that increments on every update (so the same address with a different tag fails the CAS), or deferring reclamation (hazard pointers, epoch-based reclamation) so an address can never be reused while any thread might still be referencing it.

When would you shard a data structure by ownership across threads instead of protecting one shared structure with a mutex?

When the workload can be partitioned by some stable key up front (e.g. by symbol, by customer ID, by shard index) such that items in different partitions never need to interact directly. Sharding by ownership means each partition's owning thread never needs to lock it at all — correctness comes from the fact that no other thread ever touches that memory — so N threads on N disjoint partitions run with genuinely zero contention between them, rather than being serialized by a single lock that a mutex-protected shared structure would impose regardless of whether the threads' work actually overlaps.

Decision Cheat Sheet

Protecting one flag or counter

std::atomic<T> with the narrowest memory order that's correct — relaxed for an independent counter, release/acquire for a publish/observe handshake.

Protecting more than one related piece of state

std::mutex + std::lock_guard. Atomics don't compose — making two atomics individually safe doesn't make the pair consistent.

Waiting for a condition, not just a lock

std::condition_variable with the predicate form of wait — never a bare wait(lock) without re-checking the actual condition.

Locking more than one mutex at once

std::scoped_lock (or std::lock) to acquire the full set together — never lock them one at a time in an order that could differ between threads.

"Run this and give me the result later"

std::async(std::launch::async, ...) for a one-off, or std::packaged_task feeding a thread-pool queue for repeated work — either way, mind the async future's blocking destructor.

A thread object going out of scope

std::jthread by default in new C++20 code — its destructor requests a stop and joins automatically. Otherwise, an RAII guard (§2) around a plain std::thread.

One producer, one consumer, high throughput

A bounded lock-free SPSC ring buffer with two atomic indices — no mutex needed since each side only ever writes its own index.

Many producers or many consumers on one queue

A mutex + condition_variable bounded queue is the simplest correct default; reach for a lock-free MPMC design only once profiling shows the mutex is the actual bottleneck.

N workers must all reach a point before any proceeds

std::latch for a one-time rendezvous (e.g. startup); std::barrier for a repeating one across phases.

Bounding concurrent access to a limited resource

std::counting_semaphore<N> — unlike a mutex, release doesn't have to happen on the acquiring thread.

A structure that's read by many threads, written rarely

std::shared_mutex with std::shared_lock for readers, exclusive std::unique_lock for the rare writer.

Avoiding synchronization on a hot data structure entirely

Shard by ownership (§10.1) so exactly one thread ever touches it, and route everything else through queues at the boundary.
