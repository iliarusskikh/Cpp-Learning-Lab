1
Why Smart Pointers Exist

A raw pointer answers "where is this object" but says nothing about "who is responsible for destroying it," "how many other pointers refer to it," or "is it still alive." Every bug class below comes from one of those missing answers:

Leaks

An exception or early return skips the matching delete. The allocation is never reclaimed.

Double frees

Two code paths both believe they own the pointer and both call delete on it — undefined behavior.

Dangling access

The object is freed, the pointer is not nulled, and something later dereferences the stale address.

Smart pointers solve this by binding an object's lifetime to a stack-allocated wrapper's lifetime — the idiom is called RAII (Resource Acquisition Is Initialization, covered in full in §7). When the wrapper goes out of scope, whether by falling off the end of a block, an early return, or exception unwinding, its destructor runs automatically and cleanup happens without any explicit code at the call site.

The deeper idea is that ownership becomes part of the type, not a comment or a naming convention. A function signature taking unique_ptr<T> by value is documentation that it takes ownership; one taking T& documents that it merely borrows. The compiler enforces what used to be an unenforced promise between programmers.

✓ Rule of Thumb
If you're writing new or delete directly in application code (outside of a smart pointer's own implementation), stop and ask why a smart pointer or standard container isn't doing it for you. Modern C++ style treats a bare new/delete pair as a code smell, not a default tool.

Ownership Models at a Glance

Before the mechanics of any one type, it helps to see the whole family at once. Every pointer-like tool in C++ answers the same question — "who is responsible for this object's lifetime?" — differently:

TypeOwnershipCopyable?Typical use
T* (raw pointer)None impliedYesNon-owning access; C APIs; iteration
T& (reference)None implied, never nullN/ANon-owning access when null isn't a valid state
unique_ptr<T>Exactly one ownerNo (move-only)The default owning pointer
shared_ptr<T>Shared, refcountedYesGenuinely shared lifetime across multiple owners
weak_ptr<T>None — observes a shared_ptr groupYesBreaking cycles; caches; "is it still alive?"
◆ Insight
Ownership and access are different questions. A function can access an object without owning it — that's what raw pointers, references, .get(), and weak_ptr::lock() are all for. Reach for an owning smart pointer only at the point where lifetime is actually decided; everywhere else, pass around a non-owning view.
3
std::unique_ptr

unique_ptr models exclusive ownership. Exactly one unique_ptr instance owns the managed object at any time. It is move-only — the copy constructor and copy assignment operator are deleted at compile time — so ownership can be transferred but never duplicated.

unique_ptr_basics.cpp
1 auto w = std::make_unique<Widget>(42); 2 w->process(); // use like a raw pointer 3 4 auto owner2 = std::move(w); // ownership transferred 5 // w is now nullptr — using it is a logic bug, not automatically UB, 6 // but dereferencing a null unique_ptr IS undefined behavior 7 8 // owner3 = w; // compile error: copy ctor is deleted

3.1 Key Properties

  • Zero overhead vs. a raw pointer in the common case — no atomic refcount, no control block. It's a thin RAII wrapper around a pointer plus (optionally) a deleter, and is typically exactly the size of the pointer it wraps.
  • Always prefer std::make_unique<T>(args...) over unique_ptr<T>(new T(args...)) — it avoids naming new directly and eliminates a leak edge case in function-argument evaluation order (pre-C++17, if a sibling argument's constructor threw between the new and the unique_ptr construction, the raw allocation would leak).
  • Supports custom deleters via a second template parameter, for wrapping any resource that isn't freed with plain delete.
  • reset() releases the current object (destroying it) and optionally takes ownership of a new one; release() gives up ownership without destroying, returning the raw pointer — the caller now owns it manually.
  • Implicitly convertible to bool for a null check: if (w) { ... }, mirroring raw-pointer style.

3.2 Custom Deleters

A unique_ptr isn't limited to memory freed by delete. Give it a deleter and it can manage any resource with an acquire/release pair — a file handle, a lock, a graphics handle, a database cursor. This is the same RAII idea generalized past new/delete.

file_guard.cpp
1 struct FileCloser { 2 void operator()(FILE* f) const { if (f) fclose(f); } 3 }; 4 std::unique_ptr<FILE, FileCloser> fp(fopen("data.csv", "r")); 5 // fclose(fp.get()) runs automatically when fp leaves scope — 6 // including on every early return and every exception path

A lambda works just as well as a functor when the deleter doesn't need to be reused elsewhere:

lambda_deleter.cpp
1 auto deleter = [](int* fd) { close(*fd); delete fd; }; 2 std::unique_ptr<int, decltype(deleter)> sock(new int(fd), deleter); 3 // the socket is closed automatically when sock goes out of scope
◆ Insight
A custom deleter changes the type of the unique_ptr — unique_ptr<FILE, FileCloser> and unique_ptr<FILE> are unrelated types and can't be assigned to each other. shared_ptr, by contrast, type-erases its deleter, so any shared_ptr<T> can hold any deleter without changing the type — one reason its control block exists.

3.3 Arrays

unique_ptr<T[]> (note the brackets) is specialized for arrays: it calls delete[] instead of delete, and provides operator[] instead of operator*/operator->.

unique_ptr_array.cpp
1 std::unique_ptr<int[]> buf = std::make_unique<int[]>(1024); 2 buf[0] = 7; // operator[], not operator* 3 // delete[] buf.get() runs automatically on scope exit

In practice, std::vector is almost always the better choice for a dynamically-sized array — it also tracks size and supports growth. unique_ptr<T[]> is mainly for fixed-size buffers received from a C API or for avoiding vector's default value-initialization overhead in performance-sensitive code.

std::shared_ptr

shared_ptr models shared ownership via reference counting. Multiple shared_ptr instances can point at the same object; the object is destroyed when the last one is destroyed or reset.

shared_ptr_basics.cpp
1 auto a = std::make_shared<Widget>(id); // use_count == 1 2 auto b = a; // use_count == 2, copy is allowed 3 { auto c = a; } // use_count -> 3 -> back to 2 on scope exit 4 std::cout << a.use_count(); // 2

4.1 The Control Block

Every shared_ptr group shares one heap-allocated control block holding: the strong reference count, the weak reference count, a type-erased deleter, and (for make_shared) the object itself.

FIG 1 — two shared_ptr instances referencing one control block, which owns the object
⚠ Cost
Unlike unique_ptr, shared_ptr is not free: the control block is heap-allocated (unless elided via make_shared), the refcount increment/decrement is atomic (thread-safe refcounting even in a single-threaded program), and the pointer itself is typically twice the size of a raw pointer (object pointer + control block pointer). Don't reach for shared_ptr as a default — use it only when ownership genuinely needs to be shared.

4.2 make_shared vs. shared_ptr(new T)

make_shared<T>(args...)shared_ptr<T>(new T(args...))
One allocation (object + control block combined)Two allocations — separate heap blocks
Better cache localityObject and control block can be far apart in memory
Exception-safe by constructionCan leak if used as a raw arg in a function call with unspecified evaluation order (pre-C++17)
Object memory not freed until every weak_ptr is gone tooObject destroyed as soon as strong count hits zero; control block lingers separately for weak_ptrs
Can't use a custom deleterRequired when you need a custom deleter

4.3 The Aliasing Constructor

A lesser-known but genuinely useful shared_ptr constructor lets you point at a sub-object while sharing ownership of a different object's control block. The resulting shared_ptr dereferences to the sub-object, but keeps the whole owner alive.

aliasing_ctor.cpp
1 struct Matrix { std::vector<double> data; }; 2 3 std::shared_ptr<Matrix> m = std::make_shared<Matrix>(); 4 std::shared_ptr<double> firstElem(m, &m->data[0]); 5 // firstElem.use_count() == 2 — points at a double INSIDE m, 6 // but keeps the whole Matrix alive via m's control block

4.4 enable_shared_from_this

A member function sometimes needs to hand out a shared_ptr to its own object — for example, registering this as a callback target. Constructing shared_ptr<T>(this) directly is a trap: it creates a brand-new, disconnected control block, so the object ends up owned by two unrelated refcounts and gets destroyed twice. Deriving from std::enable_shared_from_this<T> fixes this by giving the object a way to obtain a shared_ptr that shares the existing control block.

enable_shared_from_this.cpp
1 class Worker : public std::enable_shared_from_this<Worker> { 2 public: 3 void registerCallback() { 4 scheduler.onDone(shared_from_this()); // safe: reuses the real control block 5 // scheduler.onDone(shared_ptr<Worker>(this)); // BUG: second control block 6 } 7 }; 8 auto w = std::make_shared<Worker>(); 9 w->registerCallback();
⚠ Precondition
shared_from_this() only works once the object is already owned by at least one shared_ptr. Calling it from a constructor (before any shared_ptr exists yet) throws std::bad_weak_ptr.
5
std::weak_ptr

weak_ptr observes an object managed by shared_ptr without contributing to the strong reference count and without keeping it alive. It cannot be dereferenced directly.

5.1 Locking a weak_ptr

To safely access the object, first lock() it into a temporary shared_ptr, which is nullptr if the object has already been destroyed.

weak_ptr_lock.cpp
1 std::weak_ptr<Widget> observer = w; 2 if (auto locked = observer.lock()) { // promotes to shared_ptr, or null 3 locked->process(); // safe: locked keeps it alive here 4 } else { 5 // the object is already gone — handle gracefully 6 }

5.2 Breaking Reference Cycles

Two objects holding shared_ptr to each other create a reference cycle — neither strong count ever reaches zero, so neither is destroyed, even when nothing external refers to them. This is a real, common leak pattern (parent/child trees, observer graphs, doubly-linked structures). The fix is to make one direction of the relationship a weak_ptr, typically the "back" pointer (child → parent).

FIG 2 — parent owns child by shared_ptr; child refers back with weak_ptr, so the cycle can't keep both alive

5.3 Caches & Observers

Cycles aren't the only use case. Anywhere you want to refer to something without forcing it to stay alive on your account, weak_ptr fits — for example, a cache that should let entries be evicted the moment nothing else needs them:

weak_ptr_cache.cpp
1 std::unordered_map<int, std::weak_ptr<Widget>> cache; 2 3 std::shared_ptr<Widget> fetch(int id) { 4 if (auto hit = cache[id].lock()) return hit; // still alive elsewhere 5 auto fresh = std::make_shared<Widget>(id); 6 cache[id] = fresh; // observes only — doesn't pin it in memory 7 return fresh; 8 }

If the cache instead stored shared_ptr<Widget>, every entry would live forever — the cache itself would be an unbounded owner. Storing weak_ptr lets entries disappear naturally once their last real owner releases them.

⚠ Race Condition
weak_ptr::lock() is the only safe way to access the underlying object. Testing expired() and then locking separately has a race window in multithreaded code — another thread can destroy the object between the two calls. Always use the result of lock() directly.

Cost & Complexity Compared

A quick reference for the overhead each type actually carries — useful for reasoning about performance-sensitive code and for interview questions on smart pointer cost.

raw T* 1×ptr no overhead, no safety
unique_ptr 1×ptr same size, RAII, no atomics
shared_ptr 2×ptr + control block, atomic refcount
weak_ptr 2×ptr no object ownership, keeps block alive
Operationunique_ptrshared_ptr
Construction (from raw pointer)O(1), no allocationO(1), one allocation (unless make_shared shares it with the object)
CopyNot allowedO(1), atomic increment
MoveO(1), pointer swapO(1), pointer swap, no atomic op
DestructionO(1) + object destructorO(1) atomic decrement; object destructor only if count hits 0
DereferenceO(1), same as raw pointerO(1), same as raw pointer
◆ Insight
The atomic refcount in shared_ptr exists so that copies can safely cross threads — it is not optional and cannot be turned off, even in a single-threaded program. This is the single most common reason interviewers ask "why not just use shared_ptr everywhere?": the answer is the always-on atomic cost plus the extra allocation, not just "it's shared."
7
RAII: The General Principle

Smart pointers are the most common example of RAII, but RAII itself is a general C++ idiom, not a pointer-only trick: tie any resource's lifetime to a stack object's constructor and destructor. "Resource" can mean heap memory, but just as often means a mutex lock, an open file, a network connection, a database transaction, or a timing measurement.

std::lock_guard

Acquires a mutex in its constructor, releases it in its destructor — a lock that can never be forgotten, even across an exception.

std::fstream

Opens a file on construction, closes it on destruction. No matching close() call needed on any exit path.

std::vector

Owns its heap buffer the same way unique_ptr owns a single object — allocates in its constructor, frees in its destructor.

raii_generalized.cpp
1 void updateShared(SharedState& state) { 2 std::lock_guard<std::mutex> guard(state.mutex); // acquired here 3 state.mutate(); // if this throws... 4 } // ...guard's destructor still unlocks here

The pattern generalizes to a single rule: never manage a resource with a raw handle and a manual release call if a stack-lifetime wrapper can do it instead. Every smart pointer in this document is one instance of that rule applied to heap-allocated objects.

Pitfalls & Gotchas
  • Never construct two independent shared_ptr from the same raw pointer — shared_ptr<T>(raw) called twice creates two unrelated control blocks, so the object gets destroyed twice.
  • Calling .get() to obtain a raw pointer is fine for temporary use, but never store that raw pointer somewhere that outlives the smart pointer's ownership.
  • enable_shared_from_this is required if a member function needs to hand out a shared_ptr to *this — constructing one directly from this creates a second, disconnected control block (see §4.4).
  • Passing shared_ptr by value into every function "for safety" is a common overcorrection — it forces an atomic refcount bump on every call. Pass by const& if the callee doesn't need to extend ownership, or better, pass a raw pointer/reference if it doesn't need ownership involvement at all.
  • unique_ptr in a moved-from state holds nullptr — reassign or check before use; dereferencing it is undefined behavior, same as any null pointer.
  • weak_ptr::lock() is the only safe way to access the underlying object; testing expired() then locking separately has a race window in multithreaded code (see §5.3).
  • Mixing shared_ptr<T> for an array type is a historical trap — pre-C++17 it called plain delete instead of delete[] on a raw new T[n], corrupting the heap. Since C++17, shared_ptr<T[]> is supported properly and calls delete[] — but std::vector is still usually the better choice.
  • A shared_ptr cycle is a silent leak, not a crash — nothing signals it at runtime. If objects with mutual references seem to never get destroyed, suspect a missing weak_ptr before anything else.
  • Returning a smart pointer from a getter forces a choice: return const T& or a raw pointer if the caller shouldn't extend ownership; only return shared_ptr<T> if the caller genuinely needs to keep the object alive independently.

Self-Test

Tap a question to reveal the answer. Try answering in your head first — these are pitched at the level a technical interview would ask.

Why is unique_ptr move-only, and what does that buy you over shared_ptr?

Copying would imply two owners of the same object, which contradicts "exactly one owner." Disabling the copy constructor makes that contradiction a compile error instead of a runtime bug. In exchange, unique_ptr needs no refcount, no atomics, and no control block — it costs nothing more than the raw pointer it wraps.

What exactly lives in a shared_ptr's control block, and who allocates it?

The strong reference count, the weak reference count, a type-erased deleter, and (only when created via make_shared) the managed object itself, colocated in one allocation. When created via shared_ptr<T>(new T), the control block is a separate allocation from the object.

Two nodes hold shared_ptrs to each other. Neither is referenced from outside. Do they get destroyed?

No. Each keeps the other's strong count at 1, so neither ever reaches 0 — a silent leak. Fixing it means making one direction of the relationship a weak_ptr, typically the back-reference.

Why can't you safely check weak_ptr::expired() and then dereference separately in multithreaded code?

Another thread can destroy the object in the gap between the two calls. lock() is atomic with respect to the refcount — it either returns a valid shared_ptr that keeps the object alive for as long as you hold it, or a null one. Always branch on the result of lock() itself.

Why does make_shared beat shared_ptr(new T) in the common case, and when would you avoid it anyway?

make_shared does one allocation instead of two, improving cache locality and reducing allocator overhead. Avoid it when you need a custom deleter (not supported), or when the object is large and you're holding a long-lived weak_ptr to it — because the combined allocation means the object's memory isn't freed until every weak_ptr is gone too, not just every shared_ptr.

What goes wrong if a member function does `return std::shared_ptr<T>(this);`?

It creates a second control block with its own independent strong count of 1, unrelated to whatever control block (if any) already owns the object. When both control blocks eventually hit zero, the object is destroyed twice — undefined behavior. Deriving from enable_shared_from_this<T> and calling shared_from_this() reuses the real control block instead.

10
Decision Cheat Sheet

Default choice

unique_ptr. Start here for any owned heap resource. Upgrade to shared_ptr only when you can name the second owner.

Need shared ownership

shared_ptr — but confirm the lifetime actually needs multiple owners, not just multiple users.

Non-owning observer

Raw pointer or reference if lifetime is guaranteed by scope; weak_ptr if the object might outlive or be outlived unpredictably.

Breaking a cycle

One direction of a bidirectional owning relationship becomes weak_ptr.

A member handing out shared_ptr(this)

Derive from enable_shared_from_this<T> and call shared_from_this() — never construct a shared_ptr from this directly.

A non-owning cache entry

Store weak_ptr, not shared_ptr — the cache should observe, not keep entries alive forever.
