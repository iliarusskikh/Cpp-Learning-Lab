1
A Bit of History: Where "L" and "R" Come From

The terms predate move semantics entirely — they go back to C, and originally described nothing more than which side of an assignment an expression was allowed to sit on.

The Original, Purely Syntactic Definition

lvalue — short for "left value" — meant an expression that could legally appear on the left-hand side of =, because it designated an actual storage location. rvalue ("right value") meant an expression that could only appear on the right-hand side, because it was just a value with nowhere to be written back to.

c_style_lr.c
1 int x = 5; 2 x = 10; // OK — x designates storage, can sit on the left 3 10 = x; // error — 10 has no storage to assign into 4 (x + 1) = 10; // error — x + 1 is a computed value, not a location

C++ inherited this vocabulary but kept stretching it well past "which side of =" the moment references and const entered the picture — a const int& is unambiguously an lvalue (it names storage), yet it cannot legally appear on the left of =. By the time C++11 added move semantics, the assignability story had already broken down; what the language actually needed was a way to talk about identity (does this expression name a persistent object?) and resource-stealability (is it safe to cannibalize?) as two separate questions. That's the taxonomy in §2 — the "left/right" names stuck around for historical continuity, but they no longer describe the concepts they're attached to.

◆ The Names Are a Historical Accident
Don't try to derive "lvalue" and "rvalue" from first principles using the literal words "left" and "right" — it will actively mislead you once const, references, and move semantics are in play. Treat them as proper nouns for two axes defined in §2: identity and movability, not as a claim about assignment-statement geometry.
2
The Value Category Tree, Formally

Every C++ expression — not every variable, every expression — has exactly one value category, decided at compile time from two independent properties:

Has identity?

Does the expression refer to an entity that persists — something you could compare addresses of, or refer to again later? If yes, it's a glvalue.

Can be moved from?

Is it safe for a function to cannibalize the resources behind this expression, because nothing else depends on it surviving? If yes, it's an rvalue.

Cross those two yes/no questions and you get exactly three terminal categories — this is the same tree the move semantics notes introduced; the table below restates it as a truth table, which is the more useful mental model once you start classifying tricky expressions in §3.

CategoryHas identityMovable-fromColloquial gloss
lvalue✓✗"a thing with a name/address that you must not silently gut"
xvalue✓✓"a thing with a name/address that you're explicitly allowed to gut"
prvalue✗✓"a value being computed right now, with no address of its own yet"
◆ Why prvalue Isn't Just "a Copy of Rvalue"
A prvalue genuinely has no address until it's used to initialize something — 42, a + b, and Widget{} aren't "temporary objects sitting somewhere waiting to be identified"; the standard treats them as values-in-flight. This is precisely why &42 and &(a + b) are compile errors: you're asking for the address of something that, conceptually, doesn't have one yet.

glvalue (lvalue ∪ xvalue) and rvalue (xvalue ∪ prvalue) are umbrella terms layered on top of these three — useful when a rule cares about only one axis. Reference-binding rules, for instance, are usually phrased in terms of the rvalue/glvalue split rather than the three-way split directly.

3.1 The Surprising Cases

Three entries above are the ones people get wrong most often in interviews:

⚠ String Literals Are Lvalues
"hello" has type const char[6] and static storage duration — it exists for the entire program, has a real address, and you can bind an lvalue reference to it (const char (&r)[6] = "hello"; compiles fine). Every other literal (42, 3.14, true) is a prvalue; string literals are the sole exception, because they're arrays, not scalar values.
⚠ Post-Increment Forces a Copy for This Exact Reason
x++ must return a prvalue (the pre-increment value), which means it has to materialize a temporary holding the old value before incrementing x itself — that's an unavoidable extra copy that ++x doesn't pay. It's not a style preference that idiomatic C++ prefers ++it over it++ in loop headers; for non-trivial iterator types the value-category difference is a real cost.
⚠ this Is a Prvalue, but *this Is an Lvalue
It's easy to assume this behaves like any other pointer variable and is therefore an lvalue — it isn't; you can't take &this or assign to it. What you dereference to get the actual object, *this, is the lvalue, which is why return *this; in an assignment operator returns a reference correctly (see the move semantics notes, §4).
4
Reference Types & Binding Rules

References are where value categories stop being a classification exercise and start having real consequences — which reference type a given expression can bind to determines which function overload gets called, and therefore whether you copy or move.

4.1 Lvalue References — T&

A non-const lvalue reference binds only to lvalues. This is a deliberate safety rail: it stops a function from silently modifying a temporary that's about to be destroyed anyway, which is almost never what the caller meant.

lref_binding.cpp
1 void f(int& r); 2 int x = 5; 3 f(x); // OK — x is an lvalue 4 f(10); // error — 10 is a prvalue, can't bind to int& 5 f(x + 1); // error — x + 1 is a prvalue

4.2 Const Lvalue Reference Lifetime Extension

const T& is the one exception to "lvalue references need lvalues" — it can bind to an rvalue too, and when it does, the language extends the temporary's lifetime to match the reference's, instead of destroying it at the end of the full expression as would normally happen.

lifetime_extension.cpp
1 const std::string& r = std::string("temp"); 2 // normally the temporary string would be destroyed at the end of line 1 — 3 // binding it to a const& extends its lifetime to match r's scope instead 4 std::cout << r; // well-defined — the temporary is still alive here
⚠ Lifetime Extension Does Not Propagate
The extension only happens for the reference the temporary is bound to directly. If that reference is itself a class member initialized from a constructor parameter, or the temporary is returned from a function as a reference, the extension doesn't chain — you end up with a dangling reference. This is one of the more common sources of real-world use-after-free bugs in otherwise-idiomatic C++, precisely because the direct-binding case works fine and gives false confidence.

This is also why "pass by const T&" was the pre-C++11 default for avoiding unnecessary copies of large objects: it accepts both lvalues and rvalues through one signature, at the cost of never being able to move from what it receives (see the move semantics notes' rationale for why copy-and-swap instead takes its parameter by value).

4.3 Rvalue References — T&&

An rvalue reference binds only to rvalues (prvalues or xvalues) — the mirror image of a non-const lvalue reference. This is the type that overload resolution uses to route "safe to steal from" arguments into a different code path than named variables.

rref_binding.cpp
1 void g(std::string&& r); 2 std::string s = "hi"; 3 g(s); // error — s is an lvalue, won't bind to string&& 4 g(std::move(s)); // OK — std::move(s) is an xvalue 5 g(std::string("hi")); // OK — a prvalue temporary

5
Reference Collapsing

C++ doesn't allow "a reference to a reference" as something you write directly — int& & is not legal syntax. But template deduction and typedef/using substitution can produce exactly that situation indirectly, and when they do, the compiler collapses the pair down to a single reference using four fixed rules.

Written formCollapses to
T& &T&
T& &&T&
T&& &T&
T&& &&T&&
◆ The One-Line Summary
An lvalue reference is "sticky" — if either side of the collapse is &, the result is &. The result is && only when both sides are &&. This single rule is the entire mechanism behind forwarding references.
collapsing_in_practice.cpp
1 template<typename T> 2 void wrapper(T&& arg); 3 4 Widget w; 5 wrapper(w); 6 // argument is an lvalue -> T deduced as "Widget&" 7 // parameter type is literally "Widget& &&" before collapsing 8 // T& && collapses to T& -> arg's actual type is Widget& 9 10wrapper(Widget{}); 11// argument is a prvalue -> T deduced as "Widget" (no reference) 12// parameter type is "Widget &&", nothing to collapse 13// arg's actual type is Widget&&

This is exactly why the move semantics notes describe a forwarding reference as depending on deduction happening "in that same expression": deduction is the step that decides whether T becomes Widget or Widget&, and reference collapsing is the mechanical step immediately after that turns that choice into the parameter's real type. std::forward<T>(arg) works by conditionally applying std::move based on exactly this deduced T — if T collapsed to an lvalue reference, forward produces an lvalue; otherwise it produces an xvalue.

⚠ Reference Collapsing Also Applies to using/typedef and decltype
The same four rules apply anywhere a reference-to-reference could arise mechanically — not just template parameter deduction. using RRef = int&&; using LRef = RRef&; gives LRef the type int&, by the same T&& & → T& rule.
6
decltype and Value Category

decltype is the tool most directly wired into value category rules — and it has a famous quirk where wrapping an expression in an extra pair of parentheses changes its answer.

FormRule
decltype(entity)Where entity is exactly an unparenthesized variable/member name: yields the declared type of that entity
decltype(expr)For any other expression, including a parenthesized name: yields T if expr is a prvalue, T& if an lvalue, T&& if an xvalue
decltype_quirk.cpp
1 int x = 0; 2 decltype(x) a; // int — x is an unparenthesized entity name -> declared type 3 decltype((x)) b; // int& — (x) is an expression, and x-as-expression is an lvalue 4 5 struct S { int m; }; 6 S s; 7 decltype(s.m) c; // int — s.m is a member-access "entity" form 8 decltype((s.m)) d; // int& — parenthesized -> treated as expression -> lvalue -> int&
⚠ This Is a Real Bug Source in Generic Code
Code that builds a return type with auto f() -> decltype((expr)), or that uses decltype(auto), is exactly where this bites: adding or removing a seemingly-cosmetic pair of parentheses around the trailing return expression can silently switch the function from returning a value to returning a reference, changing whether callers observe modifications or get dangling references to locals. decltype(auto) in particular inherits this sensitivity — it's decltype applied to whatever the initializing expression literally is, parentheses included.

Contrast this with auto on its own, which always strips references and top-level const/volatile regardless of parentheses — auto a = (x); is always plain int, never int&. The parenthesization sensitivity is specific to decltype and decltype(auto).

7
Overload Resolution Mechanics

When several overloads differ only by reference qualifier, the compiler ranks candidates by how good a match each parameter type is for the argument's value category — this is the mechanism that makes "pass an rvalue, get the move path; pass an lvalue, get the copy path" happen automatically, with zero runtime branching.

overload_ranking.cpp
1 void process(Widget& w) { /* A: mutable lvalue only */ } 2 void process(const Widget& w) { /* B: anything, fallback */ } 3 void process(Widget&& w) { /* C: rvalues only, best for them */ } 4 5 Widget w; 6 const Widget cw; 7 process(w); // -> A (exact match, non-const beats const) 8 process(cw); // -> B (only const& can bind a const lvalue) 9 process(std::Widget{}); // -> C (rvalue&& is preferred over const& for rvalues) 10process(std::move(w)); // -> C (xvalue, same preference as above)

The ranking that makes line 9 and 10 pick C over B is a specific, memorizable rule: given a choice between an rvalue reference and a const lvalue reference, and the argument is an rvalue, the rvalue reference always wins — it's considered a strictly better match. This is precisely why adding a T&& overload next to an existing const T& overload is enough to opt a type into move semantics without touching any existing call sites: lvalues keep resolving to the old overload exactly as before, and only rvalues get rerouted.

Argument is…Candidates it can bind toWhich wins
non-const lvalueT&, const T&T& — exact match beats a match requiring an added qualifier
const lvalueconst T& onlyconst T& — the only legal candidate
rvalue (prvalue/xvalue)T&&, const T&T&& — rvalue ref beats const lvalue ref for rvalue arguments
const rvalueconst T&&, const T&const T&& if present; otherwise falls back to const T& — this is the "moving a const object falls back to copy" case, when only a non-const T&& exists
▸ Worked Example: Why This Is "Free"
Notice nothing in process's bodies branches on a runtime flag — the compiler selects among A/B/C entirely at compile time, based on the static value category of the call-site expression. This is the core payoff of the whole value-category system: move-vs-copy dispatch costs nothing at runtime because the decision was already made by the type checker.
8
The Classic Gotcha: A Named Rvalue Reference Is an Lvalue

This single fact trips up almost everyone the first time they see it, and it's the reason std::move has to be called explicitly, over and over, even inside functions that already take a T&& parameter.

⚠ The Rule
An rvalue reference variable, once it has a name, is itself an lvalue expression when you use that name. The type of the variable is "rvalue reference"; the value category of the expression consisting of its name is lvalue. Type and value category are answering different questions, and this is the case where they visibly diverge.
named_rref_is_lvalue.cpp
1 void take_by_rref(std::string&& s) { 2 std::string local = s; // COPY — s, used by name, is an lvalue 3 std::string moved = std::move(s); // MOVE — explicit cast required to move s's resource 4 }

If this weren't the rule, the parameter s inside take_by_rref would be silently movable on every use, including uses where the function still needs its value afterward — you'd get accidental double-moves or use-after-move bugs any time a function referenced its own by-rvalue-reference parameter more than once. Requiring an explicit std::move(s) each time the function actually intends to give the resource up is a deliberate safety design, not an oversight.

◆ Why This Matters for Perfect Forwarding Specifically
This is exactly why std::forward<T>(arg) is required inside a forwarding-reference function instead of just using arg directly (see the move semantics notes, §7) — arg by name is always an lvalue expression, regardless of whether the original caller passed an lvalue or an rvalue. std::forward is the mechanism that recovers the original value category from the deduced T, since the parameter's own name can no longer tell you.
▸ Contrast: Unnamed Rvalue References
A function parameter is a special case because it's named. An expression that produces an rvalue reference type without being bound to a name — like the direct result of a function call returning T&&, e.g. make_temp() where make_temp returns Widget&& — is an xvalue, not an lvalue, precisely because it has no name yet. Naming is the dividing line.
9
Pitfalls & Gotchas
  • Treating "lvalue" and "rvalue" as synonyms for "variable" and "temporary" breaks down fast — std::move(x) is an rvalue (xvalue) referring to the exact same storage as the variable x, and a function returning T& yields an lvalue that is itself a temporary-free reference to something that might outlive the call.
  • A named parameter of type T&& is an lvalue when used by its own name inside the function body — forgetting this is the single most common reason a "move" quietly turns into a copy (§8).
  • decltype(x) and decltype((x)) can differ — an extra pair of parentheses around a plain name switches decltype from "declared type" mode to "value-category-of-expression" mode (§6).
  • String literals are lvalues, not prvalues, unlike every other kind of literal — relevant when reasoning about which overload a call like f("literal") resolves to.
  • const T&& is legal and occasionally intentional (used to explicitly forbid moving from a const rvalue in an API), but it's easy to write by accident when a macro or template mechanically adds const to an already-&&-qualified type — double-check generated signatures.
  • Lifetime extension for a temporary bound to const T& only applies to the direct binding — passing that temporary through a constructor parameter or returning it by reference from a function breaks the chain and produces a dangling reference (§4.2).
  • Reference collapsing rules apply anywhere reference-to-reference could mechanically arise — not just in template argument deduction, but also through using/typedef aliases and certain decltype contexts (§5).
  • Post-increment (x++) is a prvalue and therefore necessarily materializes a temporary holding the pre-increment value, while pre-increment (++x) is an lvalue and avoids that temporary entirely — a real (if often small) performance difference for non-trivial types, not just a stylistic one.
10
Self-Test

Tap a question to reveal the answer. Try classifying each expression in your head before checking.

What value category is `"hello"` (a string literal), and why is it different from `42`?

Lvalue. Unlike numeric or boolean literals, a string literal denotes an array (const char[N]) with static storage duration — it has a real, persistent address for the whole program, which is exactly the definition of having identity. 42, by contrast, is a prvalue with no storage of its own until it initializes something.

Inside `void f(Widget&& w) { ... }`, is the expression `w` an lvalue or an rvalue?

Lvalue. The type of w is "rvalue reference to Widget," but once it has a name, using that name in an expression is an lvalue use. This is why f must write std::move(w) to actually move from it — plain w would copy.

What's the difference between `decltype(x)` and `decltype((x))` for a variable `int x`?

decltype(x) yields int — the declared type, because x is an unparenthesized entity name. decltype((x)) yields int& — the parentheses turn it into "just an expression," and x as an expression is an lvalue, so decltype's expression rule (lvalue → T&) applies.

Given overloads `void g(const Widget&)` and `void g(Widget&&)`, which one does `g(std::move(w))` call, and which rule decides it?

The Widget&& overload. std::move(w) is an xvalue, which is a kind of rvalue; when an rvalue argument can bind to both a const T& and a T&& overload, the rvalue-reference overload is ranked as the strictly better match and wins overload resolution.

What do the reference collapsing rules say happens to `T& &&`?

It collapses to T&. The rule is that an lvalue reference is "sticky" — if either side of the notional reference-to-reference is &, the result is &; only && combined with && stays &&. This exact case is what happens when a forwarding reference T&& deduces T as Widget& from an lvalue argument.

Why does `const Widget cw; process(cw);` call the `const Widget&` overload even if a `Widget&&` overload also exists?

cw is a const lvalue — it has identity and is not movable-from (it's an lvalue, plus it's const, which forbids moving from it even if it were an rvalue). A non-const Widget&& parameter can only bind to non-const rvalues, so it isn't a viable candidate at all here; const Widget& is the only overload that can legally bind a const lvalue.

11
Cheat Sheet

Classifying an expression fast

Ask two questions: does it have an address/name (identity)? Is it safe to cannibalize (movable)? Both → xvalue. Identity only → lvalue. Movable only → prvalue.

Which reference type to write

const T& to accept anything read-only; T&& to accept-and-consume rvalues specifically; T& only when you need to mutate the caller's actual object.

Forwarding reference vs. rvalue reference

T&& is a forwarding reference only if T is deduced right there (template param or auto&&); otherwise it's an ordinary, rvalue-only rvalue reference.

Using a named T&& parameter safely

Its name is an lvalue expression. Use it plainly for reads you still need; wrap it in std::move only at the one point you're done with it.

decltype parenthesization

No parens around a bare name → declared type. Any other expression, parens included → value-category-derived type (T / T& / T&&).

Reference collapsing, one line

Any & involved → result is &. Only && with && stays &&.
