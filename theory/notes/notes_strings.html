1
Where Each Type Lives

Every one of C++'s string-ish types is really just a story about ownership and storage duration. Before comparing their APIs, it helps to see where each one's bytes actually sit.

FIG 1 — a literal lives once in read-only storage; a pointer to it just holds an address; a short std::string stays inline, a long one spills to the heap

Everything that follows is really an answer to two questions: who owns these bytes, and how long do they live? Keep that frame and the rest of the API differences fall out naturally.

2
String Literals

A string literal like "hello" has type const char[6] — five characters plus the terminating null. It has static storage duration: the compiler allocates it once, and it exists for the entire lifetime of the program, typically in a read-only segment.

literal.cpp
1 const char* p = "hello"; // correct, modern form 2 char* q = "hello"; // ill-formed since C++11
⚠ Never Mutate Through a Pointer to a Literal
Writing through a pointer to a string literal is undefined behavior, even though pre-C++11 rules technically allowed binding one to a plain char*. Since C++11 that conversion no longer compiles at all — always bind literals to const char*.

Identical literals may also be deduplicated by the compiler or linker — two "hello" literals elsewhere in the program can share one storage location. It's implementation-defined, but it's one more reason a mutable pointer into a literal is dangerous: you could be corrupting a constant some other part of the program relies on.

3
Char Arrays

char arr[] = "hello"; copies the literal's bytes into a buffer you own — on the stack, in static storage, or as a class member, depending on where it's declared. Its size is fixed at compile time; there's no automatic growth.

array.cpp
1 char arr[6] = "hello"; 2 arr[0] = 'H'; // fine — this buffer is owned and mutable
⚠ Array Decay Loses the Size
sizeof(arr) gives the compile-time array size, terminator included — but an array passed to a function decays to a pointer. Inside that function, sizeof on the parameter just returns the pointer's size (4 or 8 bytes), not the string's length. Pass the length explicitly, or use a type that carries it.
4
char* and const char*

A char* is just an address. It has no ownership, doesn't manage lifetime, and doesn't know its own length — length comes from the null terminator (strlen) or from tracking it separately elsewhere.

pointer.cpp
1 const char* p = "hi"; // points at read-only literal 2 char* q = arr; // points at mutable owned memory

Whether writing through it is safe depends entirely on what it points to — a literal (never), a stack array (usually fine), or heap memory you allocated (fine, but you must free it, exactly once).

◆ Ownership Is Not In the Type
char* and const char* carry no information about who is responsible for freeing the memory they point to — that contract lives only in documentation and convention. This is precisely the gap RAII types like std::string, std::vector<char>, and std::unique_ptr<char[]> close.
5
std::string

std::string owns a dynamically managed, resizable buffer and knows its own .size(). It converts implicitly from a literal or a const char*, and hands one back out via .c_str() or .data().

string.cpp
1 std::string s = "hello"; 2 s += " world"; 3 const char* cstr = s.c_str(); // null-terminated, guaranteed since C++11

5.1 Small String Optimization

Most implementations store short strings — commonly around 15 to 22 characters, the exact threshold is implementation-defined — inline in the object itself, avoiding a heap allocation entirely. Once a string outgrows that inline buffer, it falls back to a heap-allocated one, and the object instead stores a pointer, a length, and a capacity.

✓ Repeated Append Is Cheap
+= and .append() in a loop are amortized O(1) — capacity grows geometrically. Chaining + repeatedly instead builds and discards temporaries on every step; prefer +=, .append(), or a formatting library when assembling a string.

Limited constexpr support for std::string arrived in C++20, but it's still more restricted than what std::string_view allows.

6
std::string_view

(C++17) A std::string_view is just a pointer and a length — no allocation, no ownership, and no guarantee of null-termination. It's ideal for read-only function parameters: it accepts a literal, a char[], or a std::string without copying or converting.

view.cpp
1 void log(std::string_view msg); // accepts literal, string, or char array — no copy 2 3 std::string_view danger() { 4 std::string tmp = "temporary"; 5 return tmp; // view outlives its source — dangling 6 }
⚠ It Can Dangle
A string_view doesn't extend the lifetime of what it points at, any more than a plain reference would. If the underlying std::string or buffer goes out of scope — or a std::string it aliased gets reallocated — while the view is still alive, using it is undefined behavior.

std::string_view is usable in constexpr contexts more freely than std::string, which is part of why it's the natural read-only counterpart rather than a full replacement.

8
Pitfalls & Gotchas
  • sizeof vs strlen: sizeof(arr) on a char[] is a compile-time constant — the declared size, terminator included. strlen(ptr) is a runtime O(n) walk to the first \0. Mixing them up after array-to-pointer decay is a classic bug.
  • Never let a mutable char* point at a literal — illegal since C++11, and always a bug magnet before that.
  • Raw char* ownership means no RAII — easy leaks, double-frees, and dangling pointers. Prefer std::vector<char> or std::unique_ptr<char[]> over manual new[] / delete[].
  • std::string::c_str() has always been null-terminated; since C++11, .data() is guaranteed null-terminated too, so either can go straight to a C API. std::string_view::data() carries no such guarantee.
  • A std::string_view into a std::string can dangle even without the source going out of scope — any reallocation (e.g. from appending past capacity) invalidates it, just like it would invalidate an iterator.
9
Self-Test

Tap a question to reveal the answer. Try answering in your head first.

Why is char* q = "hello"; ill-formed in modern C++, when it compiled historically?

A string literal's type is const char[N]. Binding it to a non-const char* requires an implicit const-to-non-const conversion, which C++03 allowed as a deprecated special case purely for backward compatibility with C. That conversion was removed entirely in C++11 — the correct, and now only legal, form is const char* p = "hello";.

What actually happens in memory when a std::string grows past the SSO buffer?

The object stops storing characters inline and instead allocates a heap buffer sized to the new capacity (typically growing geometrically), copies the existing characters into it, and updates its internal pointer, size, and capacity fields to describe that heap buffer. Everything holding the old inline address becomes irrelevant — but any iterator or string_view that pointed into the old inline storage is now invalidated.

Why can sizeof silently give the wrong answer for a "string length"?

Because sizeof only behaves like you'd expect on the array itself, in the scope where it's still an array. The moment that array is passed to a function, it decays to a pointer parameter, and sizeof on that parameter returns the pointer's size — 4 or 8 bytes — not the original array's length. The fix is to pass the length alongside the pointer, or use a type like std::string_view that carries its own length.

Why is a std::string_view returned from a function that built a local std::string dangerous?

The local std::string is destroyed when the function returns, freeing whatever buffer it owned (its heap allocation, or its inline SSO storage — either way, memory tied to the now-dead object). The returned string_view still holds a pointer into that freed memory, so any use of it afterward is undefined behavior, whether or not the bug happens to "look fine" in a given build.

When would you genuinely prefer a raw char[N] over std::string?

When dynamic allocation itself is the thing you're avoiding — embedded or real-time code with no heap, a fixed-format protocol buffer, or a C API that expects to write into a caller-supplied buffer of known size. Outside those cases, std::string's SSO already avoids allocation for short strings, so the manual-buffer cost rarely pays for itself.

10
Decision Cheat Sheet

Owning and mutating text

std::string. Manages its own memory, is exception-safe, and integrates with the whole standard library.

Just reading text in a function

std::string_view parameter. Accepts any source, copies nothing — but never store one past its source's lifetime.

Calling into a C API

const char*, obtained from .c_str() or .data() if you started from a std::string.

No heap allowed

A raw char arr[N], sized for the worst case, filled with snprintf or similar.

A pointer that must own its buffer

std::vector<char> or std::unique_ptr<char[]> — never a raw new[] without a matching, guaranteed delete[].

Building a string in a loop

+= or .append(), not chained + — avoids repeated temporary construction.
