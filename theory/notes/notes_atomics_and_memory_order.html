Atomics & Memory Order

How C++ atomics guarantee correctness under concurrency — from raw atomicity, to compiler/CPU reordering, to the memory_order guarantees that let threads communicate safely.

1 Why atomics exist

Two separate problems get solved by the same feature: atomicity (an operation can't be observed half-done) and ordering / visibility (when a write becomes visible to other threads, and in what order).

The torn-write problem

A plain int increment like counter++ is really three steps: load, add, store. If two threads do this concurrently without synchronization, updates can be lost — this is a data race, and it's undefined behavior in C++.

race.cpp
int counter = 0;

void worker() {
    for (int i = 0; i < 100000; ++i)
        counter++;   // NOT atomic: load, add, store — can interleave
}

// Two threads running worker() concurrently on a plain int
// will very likely produce counter < 200000. This is UB.
Key point std::atomic<int> fixes this by making the read-modify-write indivisible. That alone is what memory_order_relaxed guarantees — nothing more.

2 The reordering problem

Atomicity alone doesn't make multi-threaded code correct. The compiler and CPU are free to reorder instructions as long as a single thread can't observe the difference — but another thread watching memory absolutely can.

publish.cpp
int data = 0;
std::atomic<bool> ready{false};

// Thread A
void producer() {
    data = 42;                 // (1) ordinary write
    ready.store(true);         // (2) atomic write
}

// Thread B
void consumer() {
    while (!ready.load());     // (3) atomic read
    std::cout << data;         // (4) ordinary read — is this guaranteed to see 42?
}

Intent: A writes data, then signals ready; B waits for ready, then reads data. Without ordering guarantees this can still break:

  • The compiler/CPU may reorder (1) and (2) in thread A — ready becomes visible before data does.
  • Thread B's cache may simply not have picked up A's write to data yet, even after ready is seen as true.
  • Reordering (3) and (4) in thread B is also possible without an ordering constraint.
The core idea Memory order annotations are instructions to the compiler and CPU: "don't reorder around this operation, and make sure the right things are flushed / visible when it happens." They create a happens-before relationship between threads.

3 Memory orders

Six values, from weakest (cheapest, fewest guarantees) to strongest (most guarantees, most expensive). Stronger orders restrict what the compiler/CPU may reorder, which costs performance on some architectures (notably ARM/POWER; x86 is naturally strong for most of these).

memory_order_relaxed

Only atomicity is guaranteed. No ordering constraint on surrounding reads/writes, and no cross-thread visibility guarantee for anything else. Operations on the same atomic variable are still seen in a consistent order by all threads (modification order), but that's it.

relaxed.cpp
std::atomic<long> hits{0};

void on_request() {
    // just counting — no other memory depends on this value's timing
    hits.fetch_add(1, std::memory_order_relaxed);
}
Use it for Independent counters/statistics where you only care about the final atomic value, not about ordering it against other memory operations.

memory_order_release / memory_order_acquire

Used as a pair on the same atomic variable to create a synchronization point between two threads:

  • release (on a store): no reads/writes in this thread may be reordered after this store. All prior writes become visible to any thread that acquires this same value.
  • acquire (on a load): no reads/writes in this thread may be reordered before this load. If it observes a value written by a release, everything that happened-before the release becomes visible here.
Thread A (producer)
data = 42;
ready.store(true, release)
Thread B (consumer)
ready.load(acquire) == true
use(data); // guaranteed 42
publish_fixed.cpp
int data = 0;
std::atomic<bool> ready{false};

void producer() {
    data = 42;                                      // ordinary write
    ready.store(true, std::memory_order_release);    // publish
}

void consumer() {
    while (!ready.load(std::memory_order_acquire));  // wait for publish
    std::cout << data;                                // guaranteed to see 42
}
Mental model release = seal a package before placing it on the shelf. acquire = don't open the package until you've confirmed it's on the shelf. The synchronization only happens if the acquire actually observes that specific release's value — a stale/older read gives no guarantee.

memory_order_acq_rel

For read-modify-write operations (exchange, fetch_add, compare_exchange_*) that act as both an acquire and a release in one operation — the read part behaves like acquire, the write part like release.

acq_rel.cpp
std::atomic<int> state{0};

// Read the current state (acquire) AND publish the new state (release)
// in a single indivisible step.
int old = state.exchange(1, std::memory_order_acq_rel);

memory_order_seq_cst

The default if you omit the argument. Gives everything acq_rel gives, plus a single global total order that all threads agree on for every seq_cst operation across all atomic variables — not just the one being operated on.

Why it matters Release/acquire only orders things relative to one variable's synchronization edge. With multiple atomics involved (e.g. two flags set by two different threads, read by a third), release/acquire alone can allow surprising outcomes that seq_cst forbids by construction. It's the safe default — strongest guarantee, easiest to reason about, at some performance cost.

memory_order_consume

A weaker, data-dependency-only version of acquire: only operations that have a data dependency on the loaded value are ordered after it (not everything). In principle cheaper than acquire on some architectures.

In practice No major compiler currently implements the precise dependency-tracking semantics — they all upgrade consume to acquire under the hood. The standard itself discourages its use until it's revised. Don't reach for this in new code; use acquire.

4 Core operations

The full operation surface of std::atomic, independent of which memory order you pick.

load / store

Plain atomic read and write. The basic building block; everything else is a variant of read-modify-write.

exchange

Atomically replace the value and return the old one, as one indivisible step.

compare_exchange_strong

"If it still equals expected, set to desired." The core primitive for lock-free algorithms.

compare_exchange_weak

Same, but may fail spuriously even when the value matched — cheaper per attempt, meant for retry loops.

fetch_add / fetch_sub

Atomic read-modify-write arithmetic. Returns the old value. This is what makes counter++ safe.

fetch_and / or / xor

Atomic bitwise read-modify-write, same shape as fetch_add.

atomic_flag

The one type guaranteed lock-free on every platform. Minimal: test_and_set / clear.

wait / notify (C++20)

Block until the value changes, without spinning and without a separate mutex + condition_variable.

compare_exchange in practice — a CAS retry loop

cas_loop.cpp
std::atomic<int> x{10};

int old_val = x.load(std::memory_order_relaxed);
int new_val;
do {
    new_val = old_val * 2;   // compute the next value from what we last saw
} while (!x.compare_exchange_weak(
             old_val,                       // updated with the real value on failure
             new_val,
             std::memory_order_release,      // ordering if the swap succeeds
             std::memory_order_relaxed));     // ordering if it fails (just a read)

5 Common patterns

How the pieces above combine in real code.

5.1 Spinlock with atomic_flag

spinlock.cpp
class Spinlock {
    std::atomic_flag flag = ATOMIC_FLAG_INIT;
public:
    void lock() {
        // Spin until we're the one who flips it false -> true.
        while (flag.test_and_set(std::memory_order_acquire))
            ; // busy-wait
    }
    void unlock() {
        flag.clear(std::memory_order_release);
    }
};

acquire on lock ensures nothing inside the critical section is reordered before the lock is actually held; release on unlock ensures everything inside the critical section is visible to the next thread that acquires the lock.

5.2 Publish / ready-flag (the pattern from section 2)

One thread builds a data structure, then flips an atomic flag with release; consumers spin/wait on that flag with acquire before touching the structure. This is the single most common real-world use of release/acquire — see the fixed example in 3.2.

5.3 Lock-free stack push (CAS retry loop)

lockfree_stack.cpp
template <typename T>
struct Node { T value; Node* next; };

template <typename T>
class LockFreeStack {
    std::atomic<Node<T>*> head{nullptr};
public:
    void push(T value) {
        Node<T>* n = new Node<T>{std::move(value), nullptr};
        n->next = head.load(std::memory_order_relaxed);
        // Retry until no one else changed head under us.
        while (!head.compare_exchange_weak(
                   n->next, n,
                   std::memory_order_release,   // publish the new node + its payload
                   std::memory_order_relaxed))  // just re-reading head on failure
            ; // n->next updated to current head automatically on failure
    }
};

5.4 Atomic reference counting

refcount.cpp
std::atomic<int> refcount{1};

void add_ref() {
    // Incrementing doesn't need to synchronize with anything else yet.
    refcount.fetch_add(1, std::memory_order_relaxed);
}

void release_ref(Object* obj) {
    // Must synchronize: the thread doing the final delete needs to see
    // every other thread's writes to obj before this point.
    if (refcount.fetch_sub(1, std::memory_order_acq_rel) == 1) {
        delete obj;
    }
}
Why relaxed here, acq_rel there Incrementing a refcount doesn't need to order anything — the object is already alive and reachable. Decrementing to zero is the dangerous moment: the thread that sees the count hit zero must be guaranteed to see every prior write from every other owner, hence the acquire component on the final decrement.

6 Cheat sheet

Pick an order

  • relaxed — pure counters/stats; nothing else depends on the timing of this write.
  • release (store) / acquire (load) — "publish a finished thing"; pair them on the same variable.
  • acq_rel — read-modify-write ops that both consume prior state and publish new state (CAS, fetch_add used as a gate, refcount decrement).
  • seq_cst — default; use when multiple independent atomics interact and you don't want to reason hard about it, or when in doubt.
  • consume — avoid; compilers treat it as acquire anyway.

Rules of thumb

  • Atomicity ≠ ordering. relaxed gives you the former only.
  • A release/acquire pair only synchronizes if the acquire actually observes that release's value.
  • Use compare_exchange_weak in loops (cheaper, spurious failures expected); use _strong outside loops.
  • fetch_add/exchange/CAS return the value before the update.
  • x86 is strongly-ordered by default, so bugs from missing acquire/release often only surface on ARM/POWER — don't rely on "it worked on my machine."
