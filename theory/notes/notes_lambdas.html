1
Anatomy of a Lambda Expression

A lambda has up to six parts, most of which are optional. The full form:

capture[&total, x]
params(int n)
mutablemutable
exception specnoexcept
return type-> int
body{ return x + n; }

In practice, most lambdas only need the capture clause, parameters, and body — the compiler deduces the return type from the return statement, and mutable/noexcept are only needed in specific cases covered below.

minimal.cpp
1 auto square = [](int n) { return n * n; }; 2 square(6); // 36

Since C++17, a lambda whose captures and parameters are all usable in a constant expression can itself be constexpr (implicitly, or explicitly marked) — it can then be evaluated at compile time, e.g. as a std::array size or a template argument.

2
Capture Modes

The capture clause decides which surrounding variables the lambda's body can see, and whether it sees a copy or the original.

SyntaxMeaning
[ ]Captures nothing — body may only use its own parameters and globals.
[x]Captures x by value (a const copy, unless mutable).
[&x]Captures x by reference — body sees live changes, and can modify the original.
[=]Captures everything used in the body by value.
[&]Captures everything used in the body by reference.
[=, &total]Default by value, except total which is by reference.
[this]Captures the enclosing object by pointer — body can access members via this->.
[*this](C++17) Captures a copy of the enclosing object itself, not just a pointer.
[val = expr](C++14) Init-capture — names a new captured variable with an arbitrary initializer, e.g. to move a resource in.
FIG 1 — capture [threshold, &total] copies threshold, aliases total, and ignores log entirely
⚠ Dangling Capture
A lambda captured by reference, or by [this], is only as safe as the lifetime of what it refers to. If the lambda is stored (e.g. as a std::function callback) and outlives the local variable or the object it points to, calling it is undefined behavior — this is the single most common lambda bug in async/callback-heavy code.

2.1 Init-Capture: Moving a Resource In

An init-capture isn't limited to renaming or copying an existing variable — its initializer can be any expression, which is exactly what makes it possible to move a move-only resource (like a unique_ptr) into a lambda's closure, something plain [x] or [&x] can't do.

init_capture_move.cpp
1 auto owned = std::make_unique<Widget>(42); 2 auto task = [w = std::move(owned)]() { 3 w->process(); // the lambda now owns the Widget 4 }; 5 // owned is null here — ownership moved into task's closure

This is also the standard way to give a lambda a custom-named copy under a different name, e.g. [total = total * 2] — the left-hand name is a brand-new closure member, unrelated to whether a variable of that name exists outside.

3
const by Default, and mutable

The compiler-generated closure type's operator() is const by default. That means value-captured variables are effectively const copies inside the body — you can read them but not reassign them, even though the lambda "owns" its own copy.

mutable.cpp
1 int calls = 0; 2 auto counter = [calls]() mutable { 3 return ++calls; // legal only because of `mutable` 4 }; 5 counter(); counter(); // 1, 2 — mutates the lambda's OWN copy 6 // the outer `calls` is untouched — still 0

mutable only affects value captures. A reference capture (&calls) can already be reassigned without it, because you're modifying the original variable through the reference, not the closure's own state.

4
Generic & Templated Lambdas

C++14 allows auto parameters, which makes operator() a template — the same lambda instance works across multiple argument types, resolved at each call site.

generic.cpp
1 auto add = [](auto a, auto b) { return a + b; }; 2 add(2, 3); // int 3 add(2.5, 1.5); // double 4 add(std::string("a"), std::string("b")); // std::string

C++20 goes further and allows an explicit template parameter list, useful when you need to name the type or constrain it: []<typename T>(std::vector<T> v) { ... }.

5
Recursive Lambdas

A lambda has no name inside its own body — the name you assign it (auto factorial = ...) doesn't exist yet while the compiler is still parsing the right-hand side, so factorial(n - 1) can't be written directly inside. There are two standard workarounds.

5.1 Init-Capture a std::function Reference

recursive_std_function.cpp
1 std::function<int(int)> factorial = [&factorial](int n) -> int { 2 return n <= 1 ? 1 : n * factorial(n - 1); 3 }; 4 factorial(5); // 120

This works because factorial the variable already exists (as a std::function) by the time the lambda body actually runs, even though it didn't exist while the lambda was being defined. The capture is by reference to that outer variable, not to the lambda's own closure.

5.2 C++23: Deducing this

C++23's "deducing this" feature lets a lambda take an explicit first parameter representing itself, giving it a name to recurse through without any std::function indirection:

recursive_deducing_this.cpp
1 auto factorial = [](this auto self, int n) -> int { 2 return n <= 1 ? 1 : n * self(n - 1); 3 }; 4 factorial(5); // 120 — no std::function, no heap allocation
◆ Insight
The std::function version pays for type erasure (§8–9) on every recursive call. The deducing-this version keeps the lambda's own concrete closure type throughout the recursion — closer in cost to a hand-written recursive function.
6
What a Lambda Actually Is

A lambda expression is syntactic sugar for a compiler-generated, uniquely-named class with captured variables as data members and the body as operator(). The two are equivalent:

desugared.cpp
1 // [threshold](int x) { return x > threshold; } 2 // desugars to roughly: 3 class __lambda_anon { 4 public: 5 __lambda_anon(int t) : threshold(t) {} 6 bool operator()(int x) const { return x > threshold; } 7 private: 8 int threshold; 9 };
  • Each lambda expression has a distinct, unnamed type — two lambdas with identical source text are still different types.
  • A capture-less lambda ([]) implicitly converts to a plain function pointer, since it needs no stored state — useful for C APIs expecting a callback pointer.
  • Because the type is compiler-generated and often uninlinable-by-name, storing a lambda in auto is free; storing it in std::function is not.
✓ Where This Shows Up Elsewhere
A lambda being "just a class with a captured member and an operator()" is exactly the mechanism behind lambda-as-custom-deleter for unique_ptr: [](int* fd){ close(*fd); delete fd; } is a small closure type, and unique_ptr<int, decltype(deleter)> simply stores it as its second template argument. No special-casing is needed on the smart pointer's side.
7
Lambdas as Function Pointers

A capture-less lambda has no state to store — its closure object is empty — so the standard grants it an implicit conversion to a plain function pointer with matching signature. This is the mechanism that lets a lambda literal be dropped anywhere a C-style callback is expected: no closure object exists at the call site at all, just an ordinary code address.

7.1 Assigning to a Function Pointer

fnptr_assign.cpp
1 using BinOp = int(*)(int, int); 2 BinOp add = [](int a, int b) { return a + b; }; 3 add(2, 3); // 5 — calls through a plain function pointer, no closure object involved

Declaring add as BinOp rather than auto forces the conversion at the point of initialization. Had the lambda captured anything, this line would fail to compile — the target type has nowhere to store captured state.

7.2 Passing to a C API

The same conversion is what makes lambdas usable as callbacks for C library functions that only understand function pointers — qsort, signal, windowing-library callback registration, pthread_create, and similar APIs.

qsort_lambda.cpp
1 int data[] = {5, 2, 4, 1, 3}; 2 std::qsort(data, 5, sizeof(int), [](const void* a, const void* b) { 3 return *static_cast<const int*>(a) - *static_cast<const int*>(b); 4 }); // the lambda literal decays to int(*)(const void*, const void*) at the call site

7.3 Arrays of Function Pointers

Because each capture-less lambda decays independently, an array of them is just an ordinary array of function pointers — a common way to build an opcode table, a state-machine transition table, or a jump table without writing a named free function for every entry.

dispatch_table.cpp
1 using Op = int(*)(int, int); 2 Op table[] = { 3 [](int a, int b) { return a + b; }, // 0: add 4 [](int a, int b) { return a - b; }, // 1: sub 5 [](int a, int b) { return a * b; }, // 2: mul 6 }; 7 table[opcode](lhs, rhs); // dispatches straight off the opcode, no if/else chain
⚠ Only Capture-Less Lambdas Qualify
Every element of table above must capture nothing — a single captured handler in the mix won't compile, because Op has nowhere to store state. If a handler needs access to surrounding data (a VM's register file, an interpreter's environment), thread it through explicitly as a parameter (e.g. a Context*) rather than trying to capture it — or switch the whole table to std::function as shown in §10.1, at the cost of the erasure overhead from §8–9.

Plain function pointer (int(*)(int,int))

Only capture-less lambdas convert. Zero storage per element — ideal for large jump tables. No way to smuggle in per-entry state.

std::function<Sig>

Any lambda converts, captured or not. Each element pays for type erasure (§8–9), but entries can carry their own bound state.

8
Lambda vs. std::function

auto (the lambda's own type)

Zero overhead — same cost as a hand-written struct with the captured members inlined. Use this whenever the type can stay local: template parameters, algorithm calls, immediate use.

std::function<Sig>

Type-erased wrapper that can hold any callable matching the signature. Costs a virtual dispatch per call and typically a heap allocation for captures beyond a small-object-optimization threshold. Needed when you must store heterogeneous callables in one container, or name the type as a class member / return type.

✓ Rule of Thumb
Default to auto for locally-used lambdas (STL algorithms, immediately-invoked helpers). Reach for std::function only when you need to erase the type — e.g. storing a callback as a class member or in a container of mixed callables.
9
Capture Cost Compared

What a closure actually costs depends entirely on what it captures and how it's stored — there's no single answer to "how expensive is a lambda."

capture-less [] 0 bytes* empty class; converts to a raw fn pointer
by-value [x] sizeof(x) one member per captured variable
by-ref [&x] 1×ptr stores a reference, regardless of x's size
std::function vtable + maybe heap type erasure cost on every call

*Formally never zero (C++ objects have non-zero size so distinct instances have distinct addresses), but empty-base optimization typically makes it free in practice, and a capture-less lambda decays to a bare function pointer whenever a context needs one.

◆ Insight
Passing a lambda directly to a template (e.g. std::sort(v.begin(), v.end(), cmp)) lets the compiler see the lambda's concrete type and inline through it — often compiling down to the same code as a hand-written loop. The same lambda passed through a std::function<bool(int,int)> parameter instead loses that visibility: the call becomes an indirect (virtual-like) dispatch the compiler generally can't inline through.
10
More Use Cases & Patterns

The sections above cover the mechanics; these are the shapes lambdas actually take in day-to-day code.

10.1 Dispatch Tables With State

§7.3's function-pointer table only works when every handler is capture-less. The moment a handler needs to close over surrounding state, the table has to hold std::function instead — same dispatch-by-key shape, but each slot can now be a full closure.

command_dispatch.cpp
1 std::unordered_map<std::string, std::function<void(const Args&)>> commands = { 2 {"add", [&inventory](const Args& a) { inventory.add(a[0]); }}, 3 {"remove", [&inventory](const Args& a) { inventory.remove(a[0]); }}, 4 {"list", [&inventory](const Args&) { inventory.list(); }}, 5 }; 6 commands.at(cmd)(args); // each entry closes over the same inventory by reference

Every handler here captures inventory by reference, so the map itself must not outlive inventory — the same dangling-reference rule from §2 applies per entry.

10.2 STL Algorithms

This is the most common home for a lambda: a short predicate or transform, written inline, passed straight to an algorithm and never named.

algorithms.cpp
1 auto over = [threshold](int x) { return x > threshold; }; 2 3 std::sort(v.begin(), v.end(), [](int a, int b) { return a > b; }); // descending 4 auto it = std::find_if(v.begin(), v.end(), over); // first > threshold 5 auto n = std::count_if(v.begin(), v.end(), over); // how many > threshold 6 std::transform(v.begin(), v.end(), v.begin(), [](int x) { return x * x; }); // square in place 7 auto sum = std::accumulate(v.begin(), v.end(), 0, 8 [](int acc, int x) { return acc + (x % 2 == 0 ? x : 0); }); // sum of even elements

Every one of these passes the lambda straight into a template parameter, so per §9's insight the compiler sees the concrete closure type and typically inlines through the call — none of this pays the std::function erasure cost.

10.3 Callback Registries (Observer Pattern)

A class that lets callers register a lambda and invokes all of them later is one of the most common places a lambda ends up stored rather than called immediately.

observer.cpp
1 class Button { 2 public: 3 void onClick(std::function<void()> cb) { handlers.push_back(std::move(cb)); } 4 void click() { for (auto& h : handlers) h(); } 5 private: 6 std::vector<std::function<void()>> handlers; 7 }; 8 9 int clicks = 0; 10 Button b; 11 b.onClick([&clicks] { ++clicks; }); 12 b.onClick([] { std::cout << "clicked!\n"; }); 13 b.click(); // runs both handlers, in registration order
⚠ Same Dangling Risk as §2
b.onClick([&clicks] { ++clicks; }) is only safe as long as clicks outlives b — a std::function member is exactly the "stored callback" scenario the dangling-reference warning in §2 is about.

10.4 Returning Lambdas / Currying

A lambda's body can return another lambda, which captures whatever the outer lambda's parameters were — a small factory that bakes in one argument and hands back a callable expecting the rest.

curry.cpp
1 auto makeAdder = [](int base) { 2 return [base](int x) { return base + x; }; // inner lambda captures base BY VALUE 3 }; 4 auto add10 = makeAdder(10); 5 add10(5); // 15
⚠ Capture By Value Here Is Not Optional
If the inner lambda captured [&base] instead, it would reference a function parameter that ceases to exist the moment makeAdder returns — the returned closure would dangle on every call, immediately. Whenever a lambda is returned out of the scope that constructed it, its captures must outlive that scope, which almost always means capturing by value.

Because return-type deduction handles the nested lambda automatically (no std::function needed), each call to makeAdder produces its own distinct closure type — add10 and a hypothetical add20 are technically different types, which is fine as long as both are only ever used via auto.

11
Pitfalls & Gotchas
  • [=] and [&] capture everything the body touches, including things you might not have meant to — prefer naming captures explicitly ([threshold, &total]) once a lambda is non-trivial, both for clarity and to avoid accidental dangling references.
  • [this] captures the object by pointer, not by value — a copy of the lambda does not get a fresh copy of the object; both copies still point at the same *this.
  • Capturing a large object by value on a hot path (e.g. inside a loop passed to an algorithm) copies it on every lambda construction — capture by reference or by pointer if the lambda is constructed repeatedly.
  • An immediately-invoked lambda, []{ ... }();, is a legitimate way to initialize a const variable with multi-statement logic — don't mistake it for a mistake when reading someone else's code.
  • Prior to C++20, a structured binding (auto [a, b] = pair;) can't be captured directly by name — [a]{ return a; } is a compile error pre-C++20. The historical workaround is an init-capture with a fresh name: [a = a]{ return a; }. C++20 permits the direct form.
  • Passing a capturing lambda where a plain C function pointer is expected only compiles if the lambda captures nothing — a capturing lambda has no such conversion, since the callback signature has nowhere to store the captured state.
12
Self-Test

Tap a question to reveal the answer. Try answering in your head first — these are pitched at the level a technical interview would ask.

Why is a lambda's operator() const by default, and what does that mean for a value-captured variable?

The compiler-generated closure type defaults to a const operator(), so members holding by-value captures can be read but not reassigned inside the body — even though the lambda owns its own independent copy. Adding mutable removes that const, letting the body reassign its own copies, without affecting the original variables outside.

Why can't a lambda call itself by the name it's being assigned to?

The variable name (e.g. factorial) doesn't exist yet while the compiler is still parsing the lambda's own body — the initialization of that variable only completes once the whole expression, including the lambda, has been parsed. Working around it means either capturing a reference to an already-existing outer variable of a named type like std::function (the name exists, even though its value is still being assigned), or using C++23's deducing-this to give the lambda a self-parameter directly.

What's the difference in cost between calling a lambda via auto vs. via std::function?

Via auto, the compiler knows the lambda's exact concrete type and can inline through the call entirely — effectively free, same as a hand-written struct. Via std::function, the callable is type-erased behind a virtual-dispatch-like interface, which costs an indirect call per invocation and, for captures beyond the small-object-optimization buffer, a heap allocation on construction — and generally blocks inlining.

Why does storing `[&total]` as a callback for later use risk undefined behavior?

A reference capture doesn't extend the lifetime of what it refers to — it's just a reference, exactly like a hand-written one. If the lambda is stored (e.g. in a std::function member or an event queue) and invoked after total's scope has ended, the reference is dangling and using it is undefined behavior. This is the most common lambda bug in callback- and async-heavy code.

How would you move a unique_ptr into a lambda's closure?

With an init-capture: [w = std::move(ptr)]() { ... }. Plain captures ([w] or [&w]) can't do this — [w] would try to copy-construct, which doesn't compile for a move-only type, and [&w] would only alias the original rather than transferring ownership. The init-capture's arbitrary initializer is what makes the move possible.

13
Decision Cheat Sheet

Passed straight to an algorithm

auto / inline lambda literal. Zero overhead, and the compiler can usually inline through it.

Storing a callback as a class member

std::function<Sig> — you need a nameable type, and erasing the concrete closure type is the point.

Capturing a resource you no longer need outside

Init-capture with std::move: [x = std::move(x)].

Lambda that must recurse

std::function<Sig> self-reference for portability; deducing-this (C++23) if avoiding the erasure cost matters.

Lambda stored or returned for later use

Capture by value, not by reference — reference captures are only as safe as the lambda's own lifetime relative to what they point at.

Callback for a C API expecting a function pointer

Must capture nothing ([]) — only a capture-less lambda converts to a plain function pointer.
