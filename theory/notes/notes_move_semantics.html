Value Categories: The Full Picture

Every C++ expression has a value category. Most day-to-day reasoning only needs the lvalue/rvalue split, but the standard actually defines five categories arranged in a small tree, and interview questions on move semantics often probe the categories the simplified version glosses over.

FIG 1 — glvalue and rvalue are the two axes; xvalue is where they overlap
CategoryMeaningExample
lvalueHas identity (an address you could take), not eligible to be moved fromx, *ptr, a function returning T&
prvalue"Pure rvalue" — no identity, a value being computed, initializes something directly42, x + 1, a function returning T by value
xvalue"Expiring value" — has identity and is movable-fromstd::move(x), a function returning T&&
glvalueUmbrella term: lvalue or xvalue — anything with identity—
rvalueUmbrella term: prvalue or xvalue — anything eligible to be moved from—
◆ Why xvalue Is the Interesting Case
std::move(x) doesn't create a temporary — it produces an xvalue: an expression that still refers to x's actual storage (it has identity, you could take its address) but is now treated as safe to move from. That's the entire trick behind std::move: it doesn't change what the object is, only which overload gets picked.
value_categories.cpp
1 std::string a = "hello"; // a: lvalue 2 std::string b = a; // copy — a still needed after this line 3 std::string c = a + " world"; // (a + " world"): prvalue, a fresh temporary 4 // c can steal its buffer instead of copying 5 std::string d = std::move(a); // std::move(a): xvalue — same storage as a, but movable-from

Rvalue references, written T&&, are a reference type that can only bind to rvalues (prvalues or xvalues). Overload resolution uses this to route temporaries and std::move'd expressions into a cheaper "move" code path, and named variables into the "copy" code path, automatically.

2
std::move
💡 The One Thing to Remember
std::move does not move anything. It's a cast — static_cast<T&&>(x) — that tells the compiler "treat this lvalue as an rvalue," which makes it eligible to bind to move constructors and move-assignment operators. The actual moving happens inside whatever function receives the result.
std_move.cpp
1 std::vector<int> source = {1,2,3,4,5}; 2 std::vector<int> dest = std::move(source); 3 // dest now owns the heap buffer that source used to own 4 // source is left in a "valid but unspecified" state — 5 // typically empty for vector/string, but don't assume that generally
⚠ After a Move
A moved-from object must remain destructible and assignable — that's the only guarantee the standard makes. Reading its value (other than to reassign it) is a logic bug waiting to happen, even though it's usually not undefined behavior for standard-library types.
3
Move Constructor & Move Assignment

A class that owns a resource (heap buffer, file handle, socket) should implement both. The pattern: steal the source's internals, then null them out so the source's destructor is a no-op.

buffer.hpp
1 class Buffer { 2 public: 3 // move constructor 4 Buffer(Buffer&& other) noexcept 5 : data_(other.data_), size_(other.size_) { 6 other.data_ = nullptr; // leave source in a safe, empty state 7 other.size_ = 0; 8 } 9 // move assignment 10 Buffer& operator=(Buffer&& other) noexcept { 11 if (this != &other) { 12 delete[] data_; // release our own resource first 13 data_ = other.data_; 14 size_ = other.size_; 15 other.data_ = nullptr; 16 other.size_ = 0; 17 } 18 return *this; 19 } 20 ~Buffer() { delete[] data_; } // safe on nullptr 21 private: 22 char* data_; size_t size_; 23 };

FIG 2 — the move constructor reassigns the pointer instead of copying the bytes it points to

3.2 Why noexcept Matters Here Specifically

Standard containers like std::vector only use the move constructor during reallocation if it's marked noexcept. If it isn't, they silently fall back to copying — because if a move constructor throws partway through, the container can't safely roll back a "half moved" state. Mark move operations noexcept whenever they genuinely can't throw (which is almost always, since moving just reassigns pointers).

3.3 A Cleaner Version with std::exchange

Manually setting each stolen member to a null/zero state, as in Buffer above, is easy to get wrong when a class has several members — it's easy to forget one. std::exchange(obj, new_value) returns the old value of obj while atomically (in the code-clarity sense, not thread sense) setting it to new_value, which reads as a single clear statement instead of two:

exchange_form.cpp
1 Buffer(Buffer&& other) noexcept 2 : data_(std::exchange(other.data_, nullptr)), 3 size_(std::exchange(other.size_, 0)) {} 4 // reads as: "take other's value, and simultaneously reset it"
4
The Copy-and-Swap Idiom

Hand-written assignment operators are a common source of exception-safety bugs — if the copy of the new data throws partway through, an operator that has already torn down its own old state is left corrupted. Copy-and-swap sidesteps this: build the replacement entirely in a temporary first (where a thrown exception leaves the original object untouched), then swap, which can't throw.

copy_and_swap.cpp
1 class Buffer { 2 public: 3 Buffer(const Buffer& other) // copy ctor: deep-copies 4 : data_(new char[other.size_]), size_(other.size_) { 5 std::copy(other.data_, other.data_ + size_, data_); 6 } 7 Buffer(Buffer&& other) noexcept { swap(*this, other); } 8 9 // ONE operator= handles both copy-assign and move-assign 10 Buffer& operator=(Buffer other) noexcept { // note: by value! 11 swap(*this, other); // swap our state with the (temp) copy 12 return *this; // other's destructor cleans up our old state 13 } 14 15 friend void swap(Buffer& a, Buffer& b) noexcept { 16 std::swap(a.data_, b.data_); 17 std::swap(a.size_, b.size_); 18 } 19 private: 20 char* data_ = nullptr; size_t size_ = 0; 21 };

Taking the parameter by value is the trick that unifies copy- and move-assignment into one function: if the caller passes an lvalue, the parameter is copy-constructed (deep copy happens there, outside the operator); if the caller passes an rvalue or std::move(x), the parameter is move-constructed (cheap). Either way, operator= itself just swaps — the same few lines handle both cases correctly and cannot leak or self-destruct on self-assignment.

◆ Trade-off
Copy-and-swap is easier to get exception-safe than hand-rolling four separate special members, but it isn't always the fastest option — it can force an extra move compared to a hand-optimized move-assignment operator that reuses existing capacity (e.g. a vector's buffer if it's already large enough). Reach for it when correctness and simplicity matter more than squeezing out the last allocation.
5
The Rule of Five (and the Rule of Zero)

If a class defines any one of these, it usually needs to define — or explicitly default/delete — all five: destructor, copy constructor, copy assignment, move constructor, move assignment. Defining only some of them leads to a class that's copyable when it shouldn't be, or that silently falls back to copying when a move was intended.

SituationWhat to Do
Class owns a raw resource directlyRule of five — implement all five, or wrap the resource in a smart pointer instead
Class only holds smart pointers / standard containersRule of zero — write none of the five, let the members' own special members do the work
Class should be non-copyable, move-only= delete the copy ctor/assignment, = default the move ctor/assignment
⚠ A Common Trap
Declaring only a destructor (say, to log when an object is destroyed) silently disables the compiler-generated move constructor and move assignment — the class falls back to copying everywhere a move was expected, with no warning. If you must write a custom destructor for a class that's otherwise fine to copy/move by default, explicitly = default the other four rather than leaving them implicit.

In practice, the rule of zero is the goal: compose your class out of RAII types (unique_ptr, vector, string) so you never have to hand-write any of the five. Hand-writing them, as in the Buffer example above, is what you do inside the low-level wrapper types themselves.

6
Copy Elision & RVO

Returning a local object by value looks like it should trigger a move (or copy) into the caller's storage. Modern compilers are required (as of C++17, for the guaranteed cases) to elide that entirely — the object is constructed directly in the caller's memory, with no move or copy call at all.

rvo.cpp
1 Buffer make_buffer() { 2 Buffer b(1024); 3 return b; // NRVO: constructed directly at the call site 4 } // no move ctor call, even though Buffer has one 5 6 Buffer buf = make_buffer(); // guaranteed elision — zero copies, zero moves
💡 Common Misconception
Writing return std::move(b); here is actively harmful — it disables guaranteed copy elision (in the unnamed-return-value case) or the compiler's NRVO (in the named case) and forces an actual move constructor call where the compiler could otherwise have skipped construction entirely. Just return b;.
CaseWhat Happens
return T{...}; (unnamed temporary)Guaranteed elision since C++17 — not just permitted, mandatory. No move ctor is even required to exist.
return local; (NRVO — named local)Elision is permitted, not guaranteed, though every major compiler performs it in simple cases. A move ctor must still exist as a fallback.
return std::move(local);Forces a move, defeating both forms above. Almost always the wrong call.

Perfect Forwarding & std::forward

A function template parameter written as T&& is a forwarding reference (sometimes called a "universal reference") — not an rvalue reference — when T is itself deduced. It binds to anything, and deduces whether the argument was an lvalue or rvalue. std::forward<T> then propagates that original value category onward.

forwarding.cpp
1 template<typename T> 2 void wrapper(T&& arg) { 3 inner(std::forward<T>(arg)); // lvalue in -> lvalue out, rvalue in -> rvalue out 4 } 5 6 Widget w; 7 wrapper(w); // T deduced as Widget& -> forwards as lvalue 8 wrapper(Widget{}); // T deduced as Widget -> forwards as rvalue

This is exactly the mechanism behind std::make_unique, std::make_shared, and container emplace functions — they forward constructor arguments without forcing an extra copy, regardless of whether the caller passed a temporary or a named variable.

⚠ T&& Is Not Always Forwarding
T&& is a forwarding reference only when T is deduced in that same expression — a plain function template parameter, or auto&&. Inside a class template, void f(T&& x) where T is the class's own template parameter (already fixed when the class was instantiated) is an ordinary rvalue reference, not a forwarding one, because there's no deduction left to do at that point.
8
Cost Compared: Move vs. Copy

Move semantics only pay off for types that own an out-of-line resource. For anything else, "moving" and "copying" are the same operation under the hood.

int, double O(1) move == copy, both trivial
small struct, no heap O(1) move == copy, bytewise
std::string / vector O(1) vs O(n) move reassigns a pointer; copy duplicates n elements
unique_ptr O(1) / N-A move-only — copy doesn't compile
◆ Insight
"Small String Optimization" (SSO) is the reason a short std::string move can be just as cheap as a copy in practice — very short strings are stored inline in the object itself, with no heap buffer to steal a pointer to. Move semantics show their real advantage on large containers, where copying means an O(n) allocation-and-duplicate and moving means an O(1) pointer swap.
9
Pitfalls & Gotchas
  • Moving from a const object silently falls back to a copy — const T&& can't bind to a non-const move constructor, so overload resolution picks the copy constructor instead, with no warning.
  • Moving is not automatically cheap for every type — a small type with no heap allocation (like a plain struct of two ints) moves by copying its bytes anyway; move semantics pay off specifically for types that own a heap resource (see §8).
  • Using a variable after std::move(x) without reassigning it is a logic bug, not necessarily UB — but it's exactly the kind of bug that's easy to introduce during a refactor.
  • Returning a member by std::move from a function that also needs the object afterward silently guts it — double check lifetime before adding std::move reflexively.
  • Forwarding references (T&& in a template, with T deduced) are easy to confuse with rvalue references (T&& in a concrete, non-template context, or with T already fixed) — they look identical but behave completely differently (see §7).
  • Declaring a custom destructor (even an empty one, even just for logging) silently disables the implicitly-generated move constructor and move assignment — the class quietly falls back to copying everywhere (see §5).
  • In a range-based for (auto x : container), each x is a copy, not a move, even on the last iteration — moving out of a container element during iteration requires an explicit std::move(x) and generally shouldn't be done while still iterating over the container.
  • std::move on a const lvalue reference parameter (e.g. a function taking const T& x, then calling std::move(x) internally) still resolves to a copy — the const-ness propagates through the cast, so the "move" quietly does nothing useful.
10
Self-Test

Tap a question to reveal the answer. Try answering in your head first — these are pitched at the level a technical interview would ask.

What does std::move actually do, mechanically?

Nothing at runtime by itself — it's just static_cast<T&&>(x), producing an xvalue that refers to the same storage as x but is now eligible to bind to a move constructor or move-assignment operator. The actual stealing of resources happens inside whichever function receives that cast expression.

Why is `std::move(x)` an xvalue rather than a prvalue?

Because it still has identity — it refers to the existing object x, at x's actual address, not a freshly computed temporary. A prvalue (like a literal or a function's by-value return) has no identity at all. xvalue is exactly the overlap: identity plus movable-from.

A class defines only a custom destructor. What happens to its move constructor?

It's not implicitly generated. Declaring any of the five special members (even just the destructor) suppresses the compiler-generated move constructor and move assignment, so the class silently falls back to copying wherever a move would otherwise have been used — with no compiler warning.

Why does `return std::move(local);` usually make code slower, not faster?

It defeats copy elision / NRVO. Without the explicit std::move, the compiler is either required (unnamed temporary) or very likely (named local, via NRVO) to construct the object directly in the caller's storage — zero move or copy calls at all. Forcing std::move turns that free construction into an actual move constructor call.

Is `T&& x` in `template<typename T> void f(T&& x)` a forwarding reference or an rvalue reference?

A forwarding reference — T is deduced right there from the argument passed to f, which is the specific condition that makes T&& bind to both lvalues and rvalues. If T were already fixed before this point (e.g. it's a class template's parameter, not deduced at the call to f itself), the same syntax would be an ordinary rvalue reference instead.

Why does the copy-and-swap idiom take its assignment parameter by value instead of by const reference?

Taking it by value lets the caller's argument dictate whether a copy or a move happens, before operator= even starts: passing an lvalue copy-constructs the parameter (deep copy), passing an rvalue or std::move(x) move-constructs it (cheap). The body of operator= is then identical either way — just a swap — so one function correctly implements both copy-assignment and move-assignment.

11
Decision Cheat Sheet

Returning a local object

Just return local; — never wrap it in std::move. Let RVO/NRVO do its job.

Passing a resource you no longer need

callee(std::move(x)) — but only if you truly don't need x's value afterward.

Writing a class that owns a resource

Rule of five, or wrap the resource in an existing RAII type and get rule of zero instead.

Exception-safe assignment

Copy-and-swap: value parameter + a noexcept swap (§4) — one function, both copy- and move-assignment.

Forwarding constructor args generically

A template with T&& params (deduced) plus std::forward<T>(arg) at each use — see make_unique, emplace_back.

Move constructor with several members

Prefer std::exchange(other.member, reset_value) per member over separate assign-then-null statements.
